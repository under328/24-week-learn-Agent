## 四、Agent 方向的积累

### 4.1 CodeAgentHarness —— 我最重要的一个项目

**一句话**：跑在华为内源平台上、能做「自动改代码 + 自动代码审查」的编程智能体，我独立从 0 到 1 完成，被内部多个团队试用。

**为什么从零写 Harness（高频追问）**：
> "因为我要的是**可控性**。现成框架封装了循环，但上下文怎么裁、工具怎么失败重试、权限怎么卡，恰恰是我最需要控制的点。CodeAgentHarness 的价值不在于'能调通模型'，而在于这些 Harness 细节是我自己设计并调出来的。这也是我后来能快速上手 LangGraph 的原因——我先手写过一遍。"

**架构与实现**：

| 模块 | 做法 | 解决的问题 |
|---|---|---|
| 运行循环 | Node.js + TypeScript 实现单 Agent ReAct 循环，模型只负责推理 | 把「非推理」工作全收进 Harness，职责边界清晰 |
| 工具层 | 文件读写、代码检索、diff 生成、Shell 执行、Git 操作；TS 类型 + JSON Schema 自动生成签名 | 保证模型调用参数合法，工具可插拔复用 |
| 上下文工程 | 按文件 / 符号粒度召回相关代码，动态裁剪上下文预算 | 大仓库超窗、噪声干扰导致答偏 |
| 自动改代码 | 读码 → 定位改动点 → 生成补丁 → 输出 diff，人工确认后落盘 | 改动可控、可追溯、可回滚 |
| 自动审查 | 按「风格 → 逻辑缺陷 → 安全风险」三层输出结构化意见 + 严重度分级 | 结论可被人工快速消费 |
| 安全管控 | 工具白名单 + 读写权限分离 + 命令超时沙箱 + 敏感操作强确认 | 防止 Agent 越权改动代码库 |
| 可观测 | 分阶段耗时与 Token 打点 | 快速区分「模型问题」还是「Harness 问题」 |

**成果**：内源平台发布，被多个内部团队试用接入 ⬜【待补：如有具体数字（N 个团队 / N 个 star / 累计 N 个任务）务必填上】。

**沉淀的方法论（可迁移的部分）**：
1. 工具设计要「**签名清晰、结果结构化、失败可判别**」，否则模型反复试错烧 Token。
2. **上下文不是越多越好**——精准召回 + 主动裁剪，比全塞进去效果更好。
3. 必须有**硬性停止条件**（步数上限、重复动作检测、连续失败禁用工具），否则一定会死循环。
4. **危险操作永远要有人在环**：Agent 出建议，人做决定。
5. **可观测性是排障前提**：没有分阶段打点，就不知道问题出在模型还是代码。

### 4.2 24 周自驱训练体系

**做法**：不停在"跑通一个 demo"。**先手写、再用框架、最后要求上线**，每阶段都有可运行产出。

- **第一阶段 · 手写实现（不依赖框架）**：Pydantic v2 建模校验、httpx 连接池、asyncio（`gather` / `Semaphore` / 指数退避）；Token 与分词、上下文窗口三种裁剪策略、采样参数与 Agent 场景预设、成本核算；System Prompt 七段式设计、Few-Shot 动态选例、CoT、结构化输出多级容错；Function Calling 手写 ReAct 循环。
- **第二阶段 · RAG 与检索全链路**：四种切分策略 + ChromaDB + 增量索引（md5）；混合检索 + RRF（k=60）+ Query 改写 + 相邻块上下文扩展；LLM-as-Judge 四维评测。**关键结论：同一需求手写版约 500 行，LangChain 重构版约 200 行（↓60%）**。
- **第三阶段 · 框架、编排与上线**：LangChain 0.3 + LangGraph（StateGraph / Reducer / 条件边 / Command / 子图 / Checkpointer / interrupt）；Multi-Agent 三种编排；Golden Set、轨迹评测、pytest 回归、FastAPI 服务化、SSE、Docker Compose、Nginx、限流鉴权、Prometheus + Grafana。

**产出**：27 篇技术笔记 + 10 多个可运行项目，代表项目 5 个——Multi-Agent 研发团队协作系统、智能客服 Agent（HITL）、企业知识库 RAG Agent、带评测的 Agent 服务化上线项目、自研 ReAct 引擎 + ToolRegistry。

**怎么证明不是纸上谈兵**：随便挑一个，代码能跑、指标能说清、被追问 5 层还能接住。比如 RRF 的 k 为什么取 60——原论文推荐值，实测 40–80 差异不大，真正敏感的是召回路数而不是 k。

### 4.3 Godot 独立游戏（业余，但不要小看）

用 **Godot** 独立开发游戏原型 ⬜【待补：游戏名 / 完成度】，核心是**状态机**——用它驱动角色行为和关卡流程，管理状态迁移条件与终止条件；并用 **Python** 编写数据处理与自动化脚本。

**顺带证明**：在没有 KPI、没有老板要求的情况下，我会自己找一件事从头做到尾——这和我做 CodeAgentHarness、学 Agent 是同一个性格。

## 五、为什么转 Agent 开发工程师

### 5.1 转折点：做 CodeAgentHarness 时被"击中"了

我发现最兴奋的部分**不是**"模型能写出代码"，而是"我怎么设计工具让它少犯错""上下文怎么裁它才不糊涂""失败了怎么恢复""怎么卡住权限不让它乱改代码"。真正让我着迷的是 **Agent 的工程侧（Harness）**。

后来我看到一句话，跟我当时的感受完全对上：**Agent = Harness + Model，模型是大脑，Harness 是身体；生产级 Agent 的壁垒在 Harness，不在模型。** 模型差距在缩小，同一模型换个 Harness，任务成功率能从 40% 到 80%。**这就是我转方向的核心判断。**

### 5.2 我的能力与 Agent 岗位是同构的

| 我在客户端 / 前端积累的能力 | 直接对应的 Agent 工程能力 |
|---|---|
| ArkUI 声明式 UI 与状态管理 | LangGraph 状态图、Reducer、状态与逻辑分离 |
| 富文本增量渲染与差分更新 | 流式输出（SSE）、增量 token 渲染、增量索引 |
| 长文档性能优化、内存治理 | 上下文工程、上下文预算与截断、延迟与成本优化 |
| 组件抽象与公共组件二次封装 | Tool 抽象、ToolRegistry 工具注册中心、工具生态复用 |
| 微前端（qiankun / wujie）多应用编排 | Multi-Agent 编排与多服务组合 |
| G6 / relation-graph 知识图谱可视化 | GraphRAG、知识图谱增强检索建模与呈现 |
| 按钮级权限鉴权 | Tool Use 权限控制、敏感工具人工审批与熔断 |
| Godot 状态机驱动游戏逻辑 | ReAct 循环控制、阶段流转、终止条件与收敛保证 |

### 5.3 我不是在追热点

1. **在职期间就动手了**，不是离职后才想——CodeAgentHarness 没有 KPI、没有排期。
2. **按工程标准而不是教程标准要求自己**：手写实现 → 框架重构 → 服务化部署 → 评测回归，这条链走完了。
3. **主动补短板**：Python、后端服务化、Docker、评测体系都是我从零补起来的，且要求自己能讲清选型 trade-off。

### 5.4 我对方向的判断

模型能力会持续收敛和商品化，**差异化会转移到工程侧**：上下文工程、工具生态、错误恢复、评测与安全。客户端工程师天生对"状态、增量、性能、交互"敏感，而这些恰好是 Agent 从"能用"到"好用"的分水岭。我想长期做下去，希望三五年后能在这个方向上带团队、定标准。

## 六、高频追问 Q&A

**Q1：你是外包，是不是技术能力不行？**
> "用工形式和能力是两件事，我用产出来回答。我在外包身份下负责「华为笔记」文本笔记与富文本模块的应用层开发，是模块 owner；同时自己发起、独立完成并在华为内源平台发布了编程智能体 CodeAgentHarness，被内部多个团队试用接入。内源平台的审核和采用是技术同事用脚投票的，这比身份更能说明问题。外包编制确实有限制，比如很难参与架构选型——这也是我离开的原因之一，但不是因为能力，是因为我想做的方向在这里没有空间。"

**Q2：非科班（高分子材料），为什么能做开发？现在又转 AI？**
> "2019 年我自学转行做前端，靠的是把东西做出来——第一份工作之后就没再因为专业被质疑过。转 AI 我承认算法理论是短板，所以把力气花在工程侧，这也是我的优势区。模型原理我要求自己讲到 Transformer / Attention / SFT / RLHF 这一层，但重点投入在 Agent 工程、RAG 全链路、编排和评测上。我不装自己是算法专家，我是 Agent 工程师。"

**Q3：28 岁转行，会不会太晚？**
> "第一，我不是从零转，是把 7 年工程能力迁移到新方向；第二，Agent 工程是新领域，真正做了一两年的人也不多；第三，我这次转有真实产出——CodeAgentHarness 是内源项目，不是作业。更实际地说，我在前端和客户端积累的状态管理、性能优化、复杂交互能力，恰好是 Agent 落地时最缺的工程手感。"

**Q4：你没有正式的 Agent 岗位经验，凭什么录用你？**
> "三个来源，都不是挂名的。**一、真实内源项目**：CodeAgentHarness 独立从 0 到 1，走完设计、编码、发布、跨团队推广闭环。**二、按工程标准做的自驱项目**：Multi-Agent 协作系统、带 HITL 的智能客服、全手写 RAG 链路、FastAPI + Docker 带 Golden Set 评测的服务——每个我都能讲到 5 层追问，包括选型对比、瓶颈分析、如果重来怎么改。**三、手写过一遍底层**：ReAct 引擎、工具注册中心、RRF 融合、增量索引，不是只会调框架。我缺的是真实业务流量下的调优经验，这需要在岗位上补，但工程底子和学习速度我有信心。"

**Q5：为什么离职？为什么不留华为？**
> "一是**方向**：我想做 AI / Agent 工程，岗位是移动端业务交付，这个差异不是靠时间能解决的。二是**成长曲线**：外包编制让我很难参与架构选型和核心技术决策，这是用工形式的客观限制。我在里面拿到了最想要的东西——工程素养、鸿蒙实战、内源项目机会——但再往后，我会有更多交付经验，不会有更多 Agent 经验。所以在方向明确之后我选择离开，全职转方向。"

**Q6：空窗期在做什么？**
> "系统学 Agent，而且是按工程标准学的。24 周训练体系分三阶段：先手写实现不依赖框架，再用 LangChain / LangGraph 重构，最后要求服务化上线并带评测。产出是 27 篇技术笔记和 10 多个可运行项目。同时我在整理 GitHub，把其中 2–3 个认真开源出来。这段时间不是休息，是在给自己补履历里缺的那块。"

**Q7：CodeAgentHarness 的难点在哪？**
> "四个。**一、上下文怎么裁**：编程任务天然需要大上下文，但整仓塞进去模型会糊涂还超窗，最后按文件和符号粒度做相关性召回，再动态裁预算。**二、怎么保证它停下来**：做三层——步数硬上限、连续相同动作检测、工具连续失败就禁用。**三、怎么让它不闯祸**：工具白名单 + 读写权限分离 + 命令超时沙箱，所有改动必须输出 diff 让人确认，危险操作永远有人在环。**四、出问题怎么定位**：到底是模型能力不够还是 Harness 有 bug？没有分阶段耗时和 Token 打点根本没法回答，所以可观测是必需品。这四个问题在 LangGraph 里都有官方解法（Checkpointer、recursion_limit、interrupt、LangSmith），但我先手写过一遍，所以知道它们各自在解决什么、什么时候会不够用。"

**Q8：怎么保证学的东西不是纸上谈兵？**
> "三个标准。**能跑**——项目都是本地能跑起来的，不是笔记里的伪代码。**能说数字**——同一需求手写版 500 行、LangChain 版 200 行；RRF 的 k 取 60 是原论文推荐值，实测 40–80 差异不大，真正敏感的是召回路数；这些数字我知道怎么来的，也准备好了测试集来源和指标定义。**知道边界**——我会承认哪些是猜的、哪些没做过。编的东西经不住三层追问，所以我不编。"

**Q9：期望薪资？**
> "我这次是转方向，预期**以能力和岗位职责定，不以原来薪资为锚**。我更关注团队是不是真的在做 Agent 产品、能不能让我持续做工程纵深。薪资可以对标岗位标准。"

**Q10：给你一个 Agent 项目，3 个月怎么做？**
> "**第 0–2 周先不写 Agent**：采样 30–50 条真实问题人工分类，确认问题分布和可用知识源、评估标准——这决定后面所有选型。**第 1 个月做 MVP**：只做最核心能力，比如只接检索一个工具，用 LangGraph 搭最小状态图，同时把 Golden Set（约 100 条分层评测集）和 Trace 一起建起来——**评测从第一天就有**；目标是"准确率 > 70%、拒答率 < 20%"这条可用线。**第 2 个月按 bad case 驱动迭代**：做归因分析（检索 / 生成 / 数据问题），高频易修优先，同时补上下文工程、缓存与降级，压延迟和成本。**第 3 个月扩工具与规模化**：检索准确率稳定后再扩工具，每加一个都看工具调用准确率是否达标，补监控告警、SLO 与灰度。核心原则：**先证明价值，再扩能力；评测和可观测跟功能同步建。**"

**Q11：和纯算法背景的人比，你的优势在哪？**
> "算法理论上我不占优，所以不比这个。差异化在三点：**工程落地能力**——服务化、缓存、限流、降级、监控、回归测试，是我 7 年工程经验最熟的部分；**对体验和性能的敏感**——客户端出身让我对延迟、流式渲染、状态一致性有肌肉记忆，Agent 从"能用"到"好用"卡的就是这些；**Harness 视角**——我是从 Harness 细节出发理解 Agent 的，而行业共识恰好也是壁垒在 Harness。"

## 七、职业规划

- **0–3 个月**：吃透团队现有 Agent 系统的架构与瓶颈，从最高频 bad case 入手做出可见改进；补齐真实流量下的调优经验（限流、降级、成本、稳定性）。
- **1–2 年**：成为能独立负责一条 Agent 链路（检索 / 编排 / 工具生态 / 评测任一方向）的工程师；在 Harness 工程上形成沉淀。
- **3–5 年**：在 Agent 工程方向做纵深，能主导架构设计与技术选型；带小团队、定工程标准。

**我对自己的一句要求**：不要把"会用某个框架"当成本事，**要能讲清楚为什么这么设计、什么时候它不够用、以及我会怎么改。**
