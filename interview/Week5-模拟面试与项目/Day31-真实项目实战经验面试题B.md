## 面试速记卡

实战经验问题的回答,建议用 **"背景 → 问题 → 方案 → 结果 → 反思"** 五段式模板。这比 STAR(Situation-Task-Action-Result)多了一个"反思",而反思恰恰是区分"做过"和"学到"的关键。

```
┌─────────────────────────────────────────────────────────────────┐
│            实战经验回答模板 (BPARR 五段式)                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  B - 背景 (Background, 30 秒)                                    │
│  "我们做了一个 [项目类型] 项目,场景是 [业务场景],                    │
│   我负责 [你的角色],团队 [规模]。"                                  │
│  要点: 简洁,让面试官快速进入语境。                                   │
│                                                                 │
│  P - 问题 (Problem, 1 分钟)                                      │
│  "在 [某个阶段],我们遇到了 [具体问题]。"                             │
│  要点: 问题要具体,带量化("召回率从 72% 掉到 41%")。                   │
│  避坑: 不要说"效果不太好"这种模糊描述。                              │
│                                                                 │
│  A - 方案 (Action, 2-3 分钟)                                     │
│  "我的排查/解决过程是:                                              │
│   第一步,我 [做了什么],发现 [什么];                                  │
│   第二步,我 [做了什么],发现 [什么];                                  │
│   第三步,我 [做了什么],最终 [怎么做]。"                              │
│  要点: 讲过程不只讲结论,体现"你怎么想到的"。                          │
│  避坑: 不要跳过中间步骤直接给答案,面试官想看思路。                     │
│                                                                 │
│  R - 结果 (Result, 30 秒)                                        │
│  "最终 [指标从 X 到 Y],[业务影响]。"                                │
│  要点: 必须量化,对比"改前 vs 改后"。                                │
│  避坑: 不要只说"效果好",要说具体数字。                               │
│                                                                 │
│  R - 反思 (Reflection, 30 秒)  ★ 区分度最高                        │
│  "这次我学到的是 [方法论/原则],                                     │
│   如果重来我会 [改进点],                                            │
│   后来我把这个经验沉淀成 [SOP/工具/文档]。"                          │
│  要点: 反思要有"可迁移性",不只是"下次注意"。                         │
│  避坑: 不要说"下次会更小心",要说具体改什么。                          │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

**示例(用 BPARR 讲"chunk 切分坑")**:

> **背景**: 我们做了一个企业知识库 RAG 项目,我负责检索链路,团队 4 人。
>
> **问题**: 上线初期,用户反馈"答案经常是半截的",我们排查发现召回的 chunk 经常在表格或代码块中间被切断,准确率只有 72%。
>
> **方案**: 第一步,我写了 chunk 可视化工具,人工抽检发现 512 token 固定切分把 30% 的结构化内容切烂了; 第二步,我研究不同切分策略,改成按结构切——markdown 按标题层级、PDF 按 layout 解析、代码按函数边界,加 50 token overlap; 第三步,做 A/B 对比,固定切分 vs 结构切分,在 200 条评估集上跑。
>
> **结果**: 召回率从 72% 提到 89%,用户"答案半截"反馈下降 80%。
>
> **反思**: 我学到的是"chunk 策略比 embedding 模型更重要"——很多人只调模型不调切分。后来我把这个经验写成《RAG 切分最佳实践》文档,并把可视化工具做成团队标配,新项目直接复用。

## 易错点提醒(10 个)

回答实战经验问题时,以下 10 个陷阱要特别避开:

```
┌────────────────────────────────────────────────────────────────────┐
│  实战经验问题的 10 大易错点                                          │
├────────────────────────────────────────────────────────────────────┤
│                                                                    │
│  ❌ 1. 空谈理论,没有实战                                            │
│     错: "RAG 的核心是检索增强生成..."                                │
│     对: "我们在 RAG 项目里发现 chunk 切分粒度直接影响召回率..."        │
│     面试官要的是"你做过",不是"你知道"。                              │
│                                                                    │
│  ❌ 2. 没有量化,全是定性描述                                         │
│     错: "效果还行,用户反馈不错。"                                    │
│     对: "准确率从 72% 提到 89%,bad case 率从 18% 降到 11%。"         │
│     没数字 = 没做过 = 直接减分。                                     │
│                                                                    │
│  ❌ 3. 不说反思,只讲做了什么                                         │
│     错: 只讲方案不讲学到什么。                                       │
│     对: 方案 + "这次我学到的是...后来沉淀成..."                       │
│     反思区分"做过"和"学到"。                                         │
│                                                                    │
│  ❌ 4. 夸大贡献,把团队功劳归自己                                      │
│     错: "我把整个系统从 0 到 1 做出来。"                             │
│     对: "我负责检索链路,算法同学负责 prompt,我们协作完成。"           │
│     面试官一追问"那算法同学做了什么"就露馅。                          │
│                                                                    │
│  ❌ 5. 故事太完美,没有失败和踩坑                                      │
│     错: 全程"我选了 X,效果很好"。                                    │
│     对: "我最初选了 X,结果出了 Y 问题,后来改成 Z。"                  │
│     真实项目一定有坑,没坑的故事不可信。                               │
│                                                                    │
│  ❌ 6. 技术细节对不上(被追问就崩)                                    │
│     错: 说"用了 hybrid search"但说不清怎么融合两路结果。              │
│     对: 只讲真的搞懂的细节,不熟的就说"这部分是同事做的,我了解大致原理"。│
│     不懂装懂 = 直接出局。                                            │
│                                                                    │
│  ❌ 7. 回答太长,没有重点                                             │
│     错: 从项目背景讲到技术细节讲到团队八卦,10 分钟还没说完。           │
│     对: 用 BPARR 模板,每段控制时间,总长 5-6 分钟。                    │
│     面试官有时间预算,啰嗦 = 不会沟通。                                │
│                                                                    │
│  ❌ 8. 只讲技术,不讲业务                                             │
│     错: 只讲"我用了 X 技术"不讲"这解决了什么业务问题"。                │
│     对: 技术方案 + "这让业务方的 X 指标提升 Y%"。                     │
│     面试官招你来是解决业务问题,不是炫技。                             │
│                                                                    │
│  ❌ 9. 贬低前公司/前同事                                             │
│     错: "我们团队其他人都不懂 AI,就我一个人在做。"                    │
│     对: "团队在 AI 方面经验不多,我主动承担了 X 角色,也帮同事提升。"   │
│     贬低别人 = 贬低自己(面试官会想: 你走了会不会也这么说我)。         │
│                                                                    │
│  ❌ 10. 对"如果重来"答不上来                                          │
│      错: "应该还是这么做吧。"                                        │
│      对: "如果重来,我会: ①需求阶段就建评估集; ②..."                    │
│      "如果重来"考的是反思深度,必须有具体改进点。                       │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
```

> **评分标准**: 每题能讲出"具体问题 + 量化结果 + 反思沉淀"得满分; 缺反思扣 30%; 无量化扣 20%; 没有具体问题(只讲理论)扣 50%。

### 面试时的"三个一"原则

1. **一个完整的项目故事**: 能用 BPARR 模板讲 10 分钟不卡壳,覆盖需求→设计→实现→上线→优化→反思全链路。

## 结语

走到这里的你,已经比 90% 的"AI Agent 方向求职者"准备得更充分。这 31 天里,你从理论到实战、从代码到表达、从知识到经验,搭起了一个完整的面试准备体系。

但请记住: **面试不是终点,是起点**。

面试官问的每一个问题,本质都是在问"你能不能在我们团队里,把这件事再做一遍,而且做得更好"。所以:

- **不要背答案**: 这 31 天的内容是"脚手架",帮你搭起知识体系,真正面试时要用自己的话、自己的项目讲。

- **不要停止学习**: Agent 领域每 3 个月就有新突破,今天的"最佳实践"明天可能被颠覆。保持好奇心,保持动手能力。
