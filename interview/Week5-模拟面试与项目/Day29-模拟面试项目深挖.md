### Q1: 面试项目深挖的通用框架 — 面试官如何从项目展开追问? 你应该如何应对?

<details>
<summary>查看答案</summary>

**面试官深挖项目的 5 层追问模型**:

面试官不是随便问的,他们有一个 **"漏斗式追问"** 模型,从表层一路往下钻,每一层都在筛人:

| 层级 | 面试官的问题模式 | 他在考察什么 | 你翻车的信号 |
|------|------------------|--------------|--------------|
| L1 What | "介绍一下你做过的 Agent 项目" | 表达能力、项目重要性判断 | 啰嗦 5 分钟讲不完背景 |
| L2 How | "你这个 RAG 的召回是怎么做的?" | 技术细节真实性 | 只说"用了 LangChain",没有细节 |
| L3 Why | "为什么用 Milvus 不用 Pinecone?" | 技术选型理由、Trade-off 思考 | "网上推荐" / "同事选的" |
| L4 What if | "如果数据量再大 10 倍呢?" | 架构边界认知、扩展性思维 | "没想过" / 乱编方案 |
| L5 Reflect | "现在重做你会怎么改?" | 反思能力、技术成长 | 只会说"加缓存" / 贬低前团队 |

**L1 What — 项目陈述的黄金 60 秒**:

面试官问"介绍一下项目",你要在 **60 秒内** 给出三件事:

```
[20s] 项目是什么 + 解决什么业务问题 + 价值量化
[20s] 你的角色 + 你负责的核心模块
[20s] 技术栈一句话 + 最有亮点的一个技术决策
```

**反面教材**(真实面试常见翻车):

> "我们这个项目是做一个企业知识库的 RAG 系统,用 FastAPI 做后端,前端用 React,模型用的是 GPT-3.5,后来换成了 GPT-4,然后向量库我们对比了好几个,最后选了 Milvus,因为它是开源的,然后我们的分块策略是......"

问题: **没有业务价值、没有你的角色、没有亮点**,全在堆技术栈。

**正面示范**:

> "我主导的是一个面向企业内部的智能问答 Agent,服务 2000+ 员工,日均 query 8000 条。之前员工查制度文档平均要 8 分钟,系统上线后降到 30 秒,每月节省工时约 2400 小时。我负责整个 RAG 链路和 Agent 编排,技术栈是 Milvus + bge-large-zh + GPT-4o + 自研 ReAct 框架。最有亮点的一个决策是我们用 **LLM Rerank 替代了 Cross-Encoder**,在召回率不掉的前提下,把 P95 延迟从 4.2s 降到了 1.8s。"

**L2 How — 技术细节的"三段式回答"**:

面试官问"怎么做的",用 **决策 + 实现 + 量化** 三段式:

> **决策**: "我们选择了 **语义分块 + 父子文档** 的策略,而不是固定 512 token 分块。"
> **实现**: "具体做法是先用 bge-m3 把文档按语义切分(平均 200 token),然后把相邻 3 个 chunk 合并成一个父文档存到另一张表,召回时用子文档,生成时用父文档拼上下文。"
> **量化**: "相比固定分块,召回率从 71% 提升到 83%,而且因为父文档有更完整的上下文,幻觉率从 12% 降到了 5%。"

**L3 Why — 技术选型的"对比三件套"**:

面试官问"为什么选 X",永远不要只说 X 的优点,要说 **X vs Y vs Z 的对比 + 你的约束**:

> "当时我们对比了 Milvus、Pinecone、Qdrant 三个:
> - **Pinecone** 全托管省运维,但是数据要出境,我们企业合规不允许;
> - **Qdrant** 性能很好,但当时(2024 年初)Rust 生态、社区文档不如 Milvus 成熟;
> - **Milvus** 自托管、支持亿级向量、社区活跃,缺点是要自己运维,但我们有 K8s 团队能 hold 住。
> 所以在 **合规 + 规模 + 运维能力** 三个约束下,Milvus 是最优解。"

**L4 What if — 架构边界的"瓶颈分析"**:

面试官问"数据量大 10 倍怎么办",不要直接给方案,先 **分析瓶颈**:

> "先说清楚现在的瓶颈在哪: 当前 8000 QPS 下,瓶颈在 Rerank 阶段(GPU 利用率 80%)。如果数据量 ×10:
> - **短期**: Rerank 模型做模型蒸馏,从 bge-reranker-large 换成 distilled 版本,延迟降 60%;
> - **中期**: 把 Rerank 拆成两阶段,先用轻量双塔粗排 top-100,再用 cross-encoder 精排 top-10;
> - **长期**: 引入向量库的 IVF-PQ 索引,把召回从暴力搜降到近似搜,P99 能控制在 100ms 以内。
> 但要注意,这些优化都是 **牺牲召回率换延迟**,所以必须先有评测集来量化 trade-off。"

**L5 Reflect — 反思改进的"两层回答"**:

面试官问"重做你会怎么改",分 **技术层 + 业务层**:

> **技术层**: "如果重做,最大的改变是把 Agent 框架从自研 ReAct 换成 **Plan-and-Execute**,因为我们在实际业务里发现,ReAct 的每一步都调 LLM 做决策,延迟高且容易在长任务里跑偏。Plan-and-Execute 先规划再执行,中间步骤可以不调 LLM,延迟降一半,稳定性也好很多。"
> **业务层**: "第二个改变会更早地建评测集。我们一开始没有评测集,全靠人工 spot check,上线两周后才发现某类 query 召回很差。如果重做,我会 **第一周就拉标注团队建 500 条 golden set**,所有迭代都跑这个集合。"

**应对追问的 4 个心法**:

1. **永远先复述问题再答** —— 既能组织思路,又能确认理解一致,还能争取 3 秒思考时间。
2. **不知道就说不知道** —— 乱编的答案在 L3/L4 必穿帮,诚实 + "但我的思路是..." 比胡说加分。
3. **用数字而不是形容词** —— "效果不错" 是减分项,"P99 从 6s 降到 2.3s" 是加分项。
4. **主动留追问钩子** —— 回答里故意埋一个有趣的点(比如"这里我们踩过一个坑"),引导面试官往你准备好的方向问。

</details>

### Q2: 模拟面试 Round 1 — "介绍一下你做过的 Agent 项目" + 10 个连环追问

<details>
<summary>查看答案</summary>

**场景设定**: 你在面试某大厂 Agent 团队一面,面试官是同级工程师,风格是技术细节追问到底。

---

**面试官**: 介绍一下你做过的 Agent 项目。

**候选人(60 秒版)**:

> "我主导的是一个企业知识库智能问答 Agent,服务 2000+ 内部员工,日均 query 8000 条。业务上是替代原来的关键字搜索 + 人工查文档,把'查一个制度问题'的平均耗时从 8 分钟降到 30 秒,月节省工时 2400 小时。
>
> 我负责 RAG 全链路 + Agent 编排,技术栈是 Milvus + bge-large-zh + GPT-4o + 自研 ReAct 框架。核心亮点是用 LLM Rerank 替代 Cross-Encoder,P95 延迟从 4.2s 降到 1.8s,同时召回率不掉;另外做了一套基于 LLM-as-Judge 的离线评测闭环,把迭代周期从 2 周压到 3 天。"

---

**追问 1**: 你说"自研 ReAct 框架",为什么不直接用 LangChain 或 LlamaIndex?

**回答**:

> "三个原因:
> 1. **可控性**: LangChain 的 ReAct Agent 在我们场景下有个痛点 —— 它的 prompt 模板固化,我们要往 thought 里塞业务约束(比如'查询年假类问题必须先确认员工入职日期'),LangChain 改 prompt 要改源码,自研只需要改一个 YAML。
> 2. **延迟**: LangChain 的 Agent Executor 每一步都有大量中间对象序列化/反序列化,我们在压测时发现单步开销比裸调 OpenAI API 多 120ms,自研版直接用 dict 传递,省掉这 120ms,4 步任务省将近 500ms。
> 3. **依赖收敛**: 企业部署对第三方依赖审计很严,LangChain 一装就是 200+ 依赖,自研核心代码 800 行,审计成本可控。
>
> 当然也有代价 —— 我们没有 LangChain 丰富的工具生态,自己写了 5 个常用工具(检索/SQL/邮件/日历/审批),大概花了一周。"

---

**追问 2**: 你的 ReAct 循环怎么处理死循环? 比如工具一直返回空,Agent 一直重试。

**回答**:

> "三层防护:
> 1. **步数上限**: 硬上限 8 步,超过就强制走 fallback 回答('未找到相关文档,转人工')。
> 2. **重复检测**: 维护一个 action history,如果连续两步的 (tool, args) 完全相同,直接 break,因为这一定是死循环。
> 3. **工具失败计数**: 每个工具有独立的失败计数,连续失败 2 次就禁用该工具,并在 prompt 里告知 Agent '该工具暂不可用'。
>
> 还有一个软约束: prompt 里明确写 '如果连续 2 次检索都没找到答案,直接告诉用户未找到,不要继续尝试',这个 prompt 工程能让 80% 的潜在死循环在 LLM 层面就停掉。"

---

**追问 3**: 你说 P95 从 4.2s 降到 1.8s,这个数字怎么测的? 测试集多大?

**回答**:

> "测试集是从生产环境采样了 **500 条真实 query**(脱敏后),覆盖 5 个高频类目(请假/报销/差旅/制度/福利)。测试是在压测环境跑的,关掉缓存,每个 query 跑 3 次取中位数。
>
> 需要说明的是,这个 4.2s → 1.8s 的优化 **不只是 Rerank 的功劳**,同期还做了两件事:
> - 把 prompt 从 1800 token 压到 1100 token(清理了冗余 few-shot);
> - 向量召回从 top-20 减到 top-10(因为 LLM Rerank 的精度足够)。
>
> 所以严格说,Rerank 这一项单独贡献大概是 4.2s → 2.6s,剩下 0.8s 是 prompt 和召回数量优化。我在简历里写的是'通过 Rerank 优化把 P95 从 4.2s 降到 1.8s',这个表述确实不够严谨,应该写'Rerank + prompt 优化综合降低'。"

*(注: 主动承认表述不严谨,是面试加分项 —— 面试官最怕候选人把多个优化的功劳都算到一个技术上)*

---

**追问 4**: LLM Rerank 是用 GPT-4 还是开源模型? 成本怎么算?

**回答**:

> "用的是 GPT-3.5-turbo(当时),不是 GPT-4。原因是 Rerank 是 **排序任务不是生成任务**,只需要 yes/no 相关性判断,GPT-3.5 足够。
>
> 成本算法: 每个 query 对 top-10 候选做 Rerank,prompt 大约 1500 token(10 个 chunk 每个 150 token),输出 50 token,GPT-3.5 当时价格 $0.002/1k input + $0.002/1k output,单次 Rerank 成本约 **$0.003**。
>
> 日均 8000 query,每天 Rerank 成本 $24,月成本 $720。相比原方案 Cross-Encoder 用 GPU 推理(一张 A10 月成本约 $800),**成本降了 10%,延迟还降了**。
>
> 但有个坑: GPT-3.5 的 Rerank 偶尔会输出格式不对(比如返回 'yes' 而不是 JSON),我们加了 fallback —— 输出解析失败就退回原 Cross-Encoder,容错率 100%。

---

**追问 5**: 你的召回率 83% 是怎么算的? 召回率公式是什么?

**回答**:

> "这是 **检索召回率**,不是端到端准确率。具体定义:
>
> ```
> Recall@10 = (命中至少一个相关文档的 query 数) / (总 query 数)
> ```
>
> 判定'相关'用了 **人工标注** —— 我们让 2 个标注员对 500 条 query 各自标注 top-10 里哪些 chunk 是相关的,取交集作为 ground truth。如果 top-10 里至少有一个相关 chunk,就算命中。
>
> 需要补充的是,这个 83% 是 **Recall@10**,如果我们看 **Recall@3**(更严格,因为生成时只用 top-3),数字是 67%。这两个指标我们都会看 —— Recall@10 衡量'有没有召回上来',Recall@3 衡量'召回上来的够不够靠前'。"

---

**追问 6**: 分块策略你用的语义分块,具体怎么切的? 用的什么模型?

**回答**:

> "用的是 **bge-m3 做语义切分**,具体流程:
> 1. 文档按段落先粗切(用 markdown 的 ## 和换行);
> 2. 每个段落用 bge-m3 编码,计算相邻段落的余弦相似度;
> 3. 相似度低于阈值(我们调到 0.65)的地方切一刀;
> 4. 切完的 chunk 平均 180 token,最小 50,最大 400,超过 400 的再按句子切。
>
> 阈值 0.65 是我们 **在 100 篇文档上人工调出来的** —— 0.7 切得太碎(一个完整流程被切成两半),0.6 切得太粗(把不相关内容塞进同一个 chunk)。
>
> 另外做了 **父子文档**: 子 chunk 用来做向量召回(小、精准),父 chunk 是子 chunk 前后各扩展一个 chunk 的合并(大、上下文完整),生成时用父 chunk 拼 prompt。这个让幻觉率从 12% 降到 5%。"

---

**追问 7**: 你说服务 2000 员工,日均 8000 query,峰值 QPS 多少? 怎么扛的?

**回答**:

> "峰值 QPS 大约 15(上午 10 点和下午 3 点两个高峰)。扛的方式:
> 1. **LLM 调用**: OpenAI API 自带并发,我们设了 semaphore 限制并发 50,避免触发 rate limit。
> 2. **向量检索**: Milvus 单机 8 核 32G,IVF_FLAT 索引,nlist=512,单次召回 P99 80ms,15 QPS 完全没压力。
> 3. **缓存**: 对 query 做 embedding 后近似去重(SimHash + 汉明距离 < 3 视为相同),缓存命中率 28%,直接把 28% 的流量挡在 LLM 之前。
> 4. **降级**: Redis 延迟超 100ms 就跳过缓存,Milvus 超时 500ms 就 fallback 到 BM25。
>
> 其实 15 QPS 在 Agent 场景里算轻量,真正的瓶颈是 **LLM 的 token 速率**,GPT-4o 的 rate limit 才是天花板。我们为此做了多账号轮询 + token 桶限流。"

---

**追问 8**: 你们的评测集 500 条,怎么保证它有代表性? 会不会有采样偏差?

**回答**:

> "这是个好问题,我们也踩过坑。最初的评测集是从我自己的提问习惯采样,结果上线后发现 **一线员工的提问方式完全不同** —— 他们更口语化(比如'出差打车能报销吗'),我们评测集里全是书面化 query(比如'差旅费用报销范围')。
>
> 后来改成 **分层抽样**: 从生产日志里按 5 个类目(请假/报销/差旅/制度/福利)各抽 100 条,再按 query 长度分 3 档(短<10字/中/长>30字)均衡,最后人工筛选掉涉及隐私的。
>
> 评测集 **每季度更新一次**,把新出现的高频 query 补进去。这个机制让我们发现了一个盲区 —— 'XX 政策什么时候生效' 这类时效性问题,我们原本完全没覆盖,补进去后召回率从 83% 掉到 78%,倒逼我们加了元数据过滤(按文档生效日期)。"

---

**追问 9**: 你说做了 LLM-as-Judge 评测,LLM 当裁判可靠吗? 怎么保证一致性?

**回答**:

> "LLM-as-Judge 的问题确实是 **一致性和偏见**。我们的做法:
> 1. **双裁判**: 用 GPT-4 和 Claude-3.5 同时打分,取平均;如果两者分歧 > 2 分(5 分制),触发人工复核。
> 2. **维度拆解**: 不让 LLM 直接打'综合分',而是拆成 4 个维度(相关性/准确性/完整性/流畅度)分别打分,再加权。维度越细,LLM 越稳定。
> 3. **校准集**: 留 50 条人工双盲打分的 golden set,每次跑评测先跑这 50 条,如果 LLM 裁判和人工的 Pearson 相关系数 < 0.7,就认为裁判'跑偏了',需要调 prompt。
> 4. **顺序随机化**: 同一个 query 的两个候选回答,随机交换顺序再给 LLM 打分,消除'位置偏见'(LLM 倾向给第一个答案更高分)。
>
> 实测 GPT-4 裁判和人工的相关系数能稳定在 0.78-0.85,Claude 在 0.75-0.82,双裁判取平均后能到 0.85+。"

---

**追问 10**: 如果让你重新设计这个系统,最大的改进点是什么?

**回答**:

> "最大的改进是 **把'检索-生成'升级为'规划-检索-生成'**。
>
> 现在的系统是单轮 RAG —— 用户问一个问题,检索一次,生成一次。但实际业务里很多问题是 **多步的**,比如'我入职 3 个月能请年假吗,能请几天' —— 这需要先查年假政策(满 3 个月能不能请),再查工龄折算(3 个月折算几天),现在的单轮 RAG 召回不全。
>
> 如果重做,我会引入 **Query Decomposition** —— 用 LLM 先把复杂问题拆成子问题,每个子问题独立检索,最后合并生成。这个在学术界叫 RAG-Fusion,我们当时没做是因为优先级排在了延迟优化后面。
>
> 第二个改进是 **从 ReAct 升级到 Plan-and-Execute**,前面提到过,延迟能再降一半。第三个是 **引入用户画像** —— 不同角色的员工关心的文档不同,可以用角色信息过滤检索范围,提升召回精度。"

---

这一轮追问下来,面试官在考察的核心是 —— **你是真的做过这个项目,还是只是参与了**。10 个追问里,有 4 个是"怎么测的"(Q3/Q5/Q7/Q8),有 3 个是"为什么这么选"(Q2/Q4/Q6),有 2 个是"边界与反思"(Q9/Q10)。能扛下来,说明项目是亲手做的;扛不下来,面试官 3 个追问就能识破。

### Q3: 模拟面试 Round 2 — "你的 RAG 系统架构是什么?" + 10 个连环追问

<details>
<summary>查看答案</summary>

**场景设定**: 二面,面试官是 Tech Lead 级别,关注架构合理性和技术深度。

---

**面试官**: 你能画一下你的 RAG 系统架构吗?

**候选人(白板画图 + 口述)**:

> "整体是 **离线索引 + 在线检索 + Agent 编排** 三层。
>
> ```
> 离线索引层:
>   文档源(Confluence/Wiki/PDF)
>     → 文档解析(Unstructured)
>     → 语义分块(bge-m3, ~180 token/chunk)
>     → 父子文档(子 chunk 向量化,父 chunk 存原文)
>     → 向量入库(Milvus) + 元数据入库(PostgreSQL)
>
> 在线检索层:
>   Query → Query 改写(HyDE + 同义词扩展)
>     → 混合检索(Milvus 向量召回 top-20 + PG 全文检索 BM25 top-20)
>     → 融合(RRF Reciprocal Rank Fusion, k=60)
>     → LLM Rerank(GPT-3.5 对 top-20 打分,取 top-3)
>     → 上下文拼装(父 chunk + 元数据)
>
> Agent 编排层:
>   ReAct 循环
>     → Thought(判断是否需要工具)
>     → Action(检索/SQL/审批工具)
>     → Observation(工具返回)
>     → 循环至 Finish
>     → 流式输出(SSE)
> ```
>
> 三个核心决策点: **HyDE 做查询改写**、**RRF 做多路召回融合**、**LLM Rerank 替代 Cross-Encoder**。"

---

**追问 1**: HyDE 是什么? 为什么用它?

**回答**:

> "HyDE 是 **Hypothetical Document Embeddings** 的缩写,核心思想是 —— 与其用用户的原始 query 去检索,不如先让 LLM 生成一个'假想答案',用假想答案的 embedding 去检索。
>
> 原理: 用户的 query 通常短且是疑问句('年假怎么折算'),而文档库里的内容是陈述句('入职不满一年年假按月折算...')。直接用 query 检索,query 和文档的 **语义分布不匹配**。HyDE 先让 LLM 生成一个假想答案(可能不准,但是陈述句),用这个假想答案去检索,语义上更接近文档。
>
> 在我们的场景里,HyDE 把 Recall@10 从 76% 提到了 83%。但代价是 **多一次 LLM 调用**,延迟增加 400ms。我们用 GPT-3.5-mini 做 HyDE 生成,成本可控($0.0005/次)。"

---

**追问 2**: HyDE 生成的假想答案如果完全错了,不会误导检索吗?

**回答**:

> "会,这是 HyDE 的已知缺陷。论文里也提到,当 LLM 对问题领域不熟时,假想答案会引入噪声。
>
> 我们的缓解策略:
> 1. **不只用 HyDE 答案检索,而是 query + HyDE 答案各召回一路**,再用 RRF 融合。这样即使 HyDE 错了,原始 query 那一路还能兜底。
> 2. **HyDE prompt 里加约束**: '基于常识生成,不要编造具体数字和日期'。避免生成'年假是 15 天'这种硬编造的内容。
> 3. **对短 query 才用 HyDE**(query < 10 字),因为短 query 信息量少,HyDE 增益大;长 query 本身语义足够,不需要 HyDE。
>
> 实测加了原始 query 兜底后,HyDE 错误的 case 里仍有 70% 能通过原始 query 召回回正确文档。"

---

**追问 3**: RRF 融合的 k=60 是怎么调的? 这个参数敏感吗?

**回答**:

> "RRF 的公式是 `score(d) = Σ 1/(k + rank_i(d))`,其中 rank_i(d) 是文档 d 在第 i 路召回里的排名。
>
> k 的作用是 **控制头部和尾部权重的平衡** —— k 越小,排名靠前的文档得分优势越大(更看重'被某一路排第一');k 越大,各排名差距越小(更接近平均)。
>
> k=60 是论文原始推荐值,我们做过消融:
> - k=10: Recall@10 = 79%(太激进,头部权重过大,某一路漏掉就完了)
> - k=60: Recall@10 = 83%(最优)
> - k=100: Recall@10 = 81%(太平,失去了多路召回的意义)
>
> 结论是 **k 在 40-80 区间都不差,60 是稳健选择**,不算敏感参数。真正敏感的是'用几路召回' —— 我们试过 3 路(向量+BM25+HyDE),Recall 反而降到 80%,因为 HyDE 和向量召回相关性高,冗余了。所以 2 路(向量+BM25)是最优。"

---

**追问 4**: 你说父子文档,如果父 chunk 太长塞不进 prompt 怎么办?

**回答**:

> "父 chunk 平均 540 token(3 个子 chunk 合并),加上 top-3 召回,总上下文 1620 token,加上 system prompt 和 query,总输入约 2800 token,GPT-4o 的 128k 上下文完全够用。
>
> 但我们确实遇到过 **极端 case** —— 某些制度文档一个章节就有 3000 token,父 chunk 直接爆炸。处理方式:
> 1. **父 chunk 也有上限**: 超过 800 token 的父 chunk,从中间再切,保留中间部分(因为子 chunk 在中间)。
> 2. **分层父子**: 子 chunk 的父 chunk 不一定是相邻 3 个,而是 **同一个 markdown section 内的所有 chunk**。这样上下文更完整,且 section 本身有天然边界。
> 3. **LLM 压缩兜底**: 如果拼装后还是超过 4000 token,用 GPT-3.5 做一次摘要,把 3000 token 压到 800 token 再喂给 GPT-4o 生成。这个兜底触发率 < 2%。"

---

**追问 5**: 元数据过滤你做了哪些维度? 怎么实现的?

**回答**:

> "三个维度:
> 1. **部门**: 30 个部门,用 PG 的 `department` 字段过滤。员工查'差旅标准'时,先按自己部门过滤,避免召回别的部门的差旅标准(各部门标准不同)。
> 2. **生效日期**: 用 `effective_date` 和 `expire_date` 过滤,只召回当前生效的文档。这个解决了'查到了 2019 年的旧政策'的问题。
> 3. **文档类型**: 区分'制度/操作指南/FAQ',FAQ 类问题优先召回 FAQ 文档。
>
> 实现上,Milvus 2.4+ 支持 **标量字段过滤**,我们在向量入库时同时存 metadata,检索时用 `expr="department == 'R&D' and effective_date <= NOW() and expire_date > NOW()"` 做预过滤,再向量搜索。性能损耗约 5%,但召回精度提升明显 —— 加了部门过滤后,跨部门误召回从 11% 降到 1.2%。"

---

**追问 6**: 向量维度多少? 用的是 bge-large-zh 是 1024 维,为什么不用更小的模型?

**回答**:

> "bge-large-zh 是 1024 维。选型时对比过:
> - **bge-small-zh (512 维)**: 召回率 76%,延迟 12ms
> - **bge-base-zh (768 维)**: 召回率 80%,延迟 18ms
> - **bge-large-zh (1024 维)**: 召回率 83%,延迟 25ms
>
> 我们的场景是 **企业知识库,文档量 50 万 chunk**,对召回率敏感(差几个点用户体验差异大),对延迟相对不敏感(本来就是 30 秒级任务,25ms vs 12ms 无感)。所以选 large。
>
> 代价是 **存储成本**: 50 万 × 1024 维 × float32 = 2GB,加上 HNSW 索引膨胀 3 倍,共 6GB,Milvus 单机完全 hold 住。如果是亿级向量,会考虑 bge-base + PQ 量化。"

---

**追问 7**: 你的系统怎么处理用户问的是闲聊(比如'今天天气怎么样'),而不是知识库问题?

**回答**:

> "这个用了一个 **意图分类器** 做前置路由:
> 1. 用 GPT-3.5-mini 做意图分类,输出 `{'intent': 'kb_query'|'chitchat'|'task'}`,延迟 200ms,成本 $0.0003。
> 2. `chitchat` 直接走 LLM 自由对话,不检索,省掉 RAG 全链路延迟。
> 3. `task` 走 Agent 工具调用链路(比如'帮我请个假'触发审批工具)。
> 4. `kb_query` 才走完整 RAG。
>
> 这个分类器让 30% 的闲聊流量绕开了 RAG,整体 P50 延迟从 2.1s 降到 1.4s。
>
> 分类器准确率 94%,误判的 6% 主要是'边界 query'(比如'年假和事假哪个更划算'被分类成 chitchat)。我们用 **兜底策略**: 如果 chitchat 链路的 LLM 输出里出现了'建议您查询'这种表述,自动 fallback 到 RAG 重跑。"

---

**追问 8**: 增量更新怎么做的? 文档改了怎么同步到向量库?

**回答**:

> "文档源是 Confluence,我们订阅了它的 webhook,文档变更时触发更新。流程:
> 1. **Webhook 推送 doc_id**,我们去 Confluence 拉最新内容。
> 2. **Diff 对比**: 用 difflib 对比新旧文档,找出变更的段落(而不是整篇重新切分)。
> 3. **局部重建**: 只对变更段落重新分块、重新向量化,删掉旧 chunk,插入新 chunk。
> 4. **版本管理**: Milvus 里保留旧版本 chunk(带 `version` 字段),新版本立即生效,旧版本保留 7 天用于回滚。
>
> 这个设计的关键是 **局部重建**,一篇 10000 字的文档如果只改了 1 段,只需要重新向量化 1 个 chunk 而不是 50 个,更新延迟从 30s 降到 2s。
>
> 坑: Confluence 的 webhook 偶尔丢消息,我们加了 **每日全量对账** —— 凌晨 3 点跑一个 job,对比 Confluence 所有文档的 `last_modified` 和 Milvus 里的 `indexed_at`,不一致的重新索引。"

---

**追问 9**: 如果向量库挂了,系统怎么办?

**回答**:

> "三层降级:
> 1. **L1 - Milvus 副本**: Milvus 本身是分布式,2 副本,单节点挂自动切换。
> 2. **L2 - BM25 兜底**: 如果整个 Milvus 集群不可用,检索层自动 fallback 到 PostgreSQL 的全文检索(BM25)。虽然召回率从 83% 掉到 68%,但至少能用。
> 3. **L3 - 缓存兜底**: 如果 PG 也挂,走 Redis 缓存,命中率 28% 的 query 能直接返回历史答案。
> 4. **L4 - 直连 LLM**: 全挂了就跳过检索,直接让 LLM 用自己的知识回答,并在回答前加 disclaimer '当前知识库不可用,以下回答未经文档验证'。
>
> 这套降级链路我们 **每月做一次混沌演练**,故意 kill Milvus,验证 fallback 是否生效。有一次发现 BM25 fallback 的超时阈值设成了 5s(太长),用户感知到卡顿,调到 1s 后解决。"

---

**追问 10**: 你这套架构,如果文档量从 50 万 chunk 涨到 5000 万,哪些地方会先撑不住?

**回答**:

> "瓶颈分析:
> 1. **向量库**: 5000 万 × 1024 维 × 4 字节 = 200GB 向量数据,HNSW 索引膨胀 3 倍 = 600GB,单机存不下。需要 Milvus 集群版 + 分片,或者上 IVF-PQ 量化(精度掉 3-5%,存储省 8 倍)。
> 2. **检索延迟**: HNSW 在 5000 万规模下 P99 会从 80ms 涨到 300ms+,需要调 `ef_search` 参数,或者上 GPU 索引(RAPID)。
> 3. **索引构建**: 5000 万 chunk 重新建索引要 10+ 小时,需要做 **增量索引** 而不是全量重建。Milvus 2.4+ 支持增量 upsert,但要监控 segment 数量,太多会拖慢查询。
> 4. **BM25 那一路**: PG 全文检索在 5000 万行时性能急剧下降,需要换 Elasticsearch。
> 5. **LLM Rerank**: top-20 的 Rerank 不受影响,但如果要扩到 top-100,成本和延迟都翻 5 倍,需要换成两阶段 Rerank(双塔粗排 + cross-encoder 精排)。
>
> 真正难的不是单点扩容,而是 **混合检索的协同** —— 向量库和 ES 的分片策略要对齐,否则 RRF 融合时排名会失真。这个在 5000 万规模下是架构级挑战,需要专门的检索平台团队来做。"

---

**面试官小结**:

这一轮架构深挖,核心是看候选人 **有没有架构演进的预见性**。能在 L4-L5 追问里答出"瓶颈在哪、怎么拆、trade-off 是什么",说明不只是画过架构图,而是真的压测过、踩过坑。答不上来的候选人,通常只能停在"我用了 X 技术",问到规模就崩。

### Q4: 模拟面试 Round 3 — "你遇到最难的 Agent 问题是什么? 怎么解决的?" + 追问(STAR 回答)

<details>
<summary>查看答案</summary>

**场景设定**: 三面,面试官是团队负责人,关注解决问题的能力和方法论。

---

**面试官**: 说一个你做 Agent 项目里最难的问题,怎么解决的?

**候选人(STAR 完整版)**:

> **Situation(背景)**:
> "系统上线 3 个月后,业务方反馈一个奇怪的现象 —— 某些 query 的回答 **时好时坏**,同样的问法,早上问和下午问结果不一样。我们一开始以为是 LLM 的随机性,但排查后发现,同样的 query 在 **不同时间段命中率差异高达 30%**,这不是 LLM 随机性能解释的。
>
> 这个问题困扰了我们 2 周,因为是 **间歇性故障**,复现困难,业务方已经开始失去信任,有部门提出要回退到旧的搜索系统。
>
> **Task(我的任务)**:
> 作为项目技术负责人,我需要在 1 周内定位根因并修复,否则系统会被下线。具体要回答三个问题: 为什么会时好时坏? 怎么稳定复现? 怎么彻底修复?
>
> **Action(我的行动)**:
>
> 第一步 **建复现脚本**: 我先写了 100 条稳定 query,每 30 分钟跑一次,记录召回率和生成质量。跑了一天发现 **召回率在下午 2-4 点会从 83% 掉到 55%**,其他时段正常。这是关键线索 —— 时间相关性极强。
>
> 第二步 **按时间维度排查**: 2-4 点发生了什么? 排查了几个假设:
> - *假设 1: LLM API 限流* —— 查了 OpenAI dashboard,2-4 点的 429 错误率正常(<0.1%),排除。
> - *假设 2: 数据库慢查询* —— 查 PG 慢日志,2-4 点确实有慢查询,但都在 200ms 内,不至于影响召回。部分排除。
> - *假设 3: 向量库性能波动* —— 查 Milvus 监控,发现 2-4 点 Milvus 的查询延迟 P99 从 80ms 涨到 600ms,且 **CPU 使用率飙到 95%**。这是强相关。
>
> 第三步 **定位 Milvus 异常**: 为什么 2-4 点 CPU 飙升? 查 Milvus 的 compaction 日志,发现 **compaction 任务默认在低峰期跑(凌晨配置成了下午 2 点,这是个配置错误)**,compaction 时会重建索引,CPU 拉满,查询性能急剧下降。
>
> 第四步 **修复**: 三个动作:
> 1. 把 compaction 时间改回凌晨 3 点(配置修复);
> 2. Milvus 升级到 2.4,启用 **并行 compaction + 查询隔离**,compaction 期间查询走旧 segment,不受影响;
> 3. 加了 **查询延迟监控告警**,P99 > 200ms 自动报警。
>
> **Result(结果)**:
> 修复后连续观察 2 周,召回率稳定在 83%±2%,再无时段性波动。业务方撤回回退要求,系统保住了。
>
> 更重要的 **副产品** —— 我把这次的排查过程做成了一个 **'检索稳定性 SLO'文档**,定义了 P99 延迟 < 200ms、召回率波动 < 5% 等 5 个 SLO 指标,接入了 Prometheus 告警。这个 SLO 后来成了团队所有 RAG 项目的标配。"

---

**追问 1**: 你怎么想到去查 Milvus 的 compaction? 这个排查思路是怎么形成的?

**回答**:

> "说实话,第一反应不是查 compaction,而是怀疑 LLM。是 **'时间相关性'这个线索逼着我往基础设施层查**。
>
> 排查思路其实是一个 **'分层下钻'** 流程:
> 1. 先看应用层(LLM 输出是否波动)→ 排除,因为检索召回率本身就波动;
> 2. 再看检索层(向量库 + BM25)→ 发现向量库延迟波动;
> 3. 再看基础设施(Milvus 内部)→ 发现 compaction。
>
> 这个思路的底层逻辑是 **'波动一定是某个组件的状态在变'**,而状态变化通常和 **时间、负载、配置变更** 相关。时间相关性最强,所以先按时间维度切。我之前做 SRE 的经验帮上忙了 —— SRE 的排查套路就是'先找相关性,再找因果'。"

---

**追问 2**: 这个问题如果是你同事遇到的,你怎么帮他更快定位?

**回答**:

> "我后来做了一个 **'RAG 故障排查决策树'**,把这个经验沉淀下来:
>
> ```
> 召回率波动?
> ├─ 是 → 按时间切片看波动规律
> │   ├─ 有规律 → 检查定时任务(compaction/备份/ETL)
> │   └─ 无规律 → 检查负载相关(缓存命中率/并发量)
> └─ 否 → 检查 query 分布是否有变化(新业务上线?)
> ```
>
> 同事遇到类似问题,先跑这个决策树,能省掉 80% 的试错时间。这个决策树我们放进了团队 wiki,后续又补充了'生成质量波动''延迟波动'两个分支。"

---

**追问 3**: 你说做了 SLO,这个 SLO 怎么定义的? 怎么保证它能落地?

**回答**:

> "SLO 定义遵循 Google SRE 的 **'用户感知优先'** 原则:
>
> | SLO 指标 | 目标 | 用户感知 |
> |---------|------|----------|
> | 检索 P99 延迟 | < 200ms | 用户感觉'快' |
> | 召回率(日均值) | > 80% | 用户感觉'答得对' |
> | 召回率波动(日间) | < 5% | 用户感觉'稳定' |
> | 生成 P99 延迟 | < 3s | 用户感觉'能等' |
> | 端到端可用性 | > 99.5% | 用户感觉'能用' |
>
> 落地的关键是 **Error Budget** —— 每月允许 0.5% 的不可用时间(约 3.6 小时)。如果一个月内 Error Budget 用掉一半,开发暂停,优先修稳定性;如果用完了,停止发新功能。这个机制让团队 **不敢忽视 SLO**,因为超了真的不能发版。"

---

**追问 4**: 这个问题根因是配置错误,你怎么避免类似问题再发生?

**回答**:

> "三个机制:
> 1. **配置审计**: 所有定时任务配置进 Git,PR review 合并,不允许在 admin 后台直接改。这次的问题就是有人在后台改了 compaction 时间没记录。
> 2. **配置基线测试**: 加了一个 CI job,每次配置变更后跑 24 小时回放测试,对比关键指标。如果召回率波动 > 5%,阻断发布。
> 3. **混沌演练常态化**: 每月一次,模拟'compaction 期间流量高峰''LLM 限流''向量库单节点挂'等场景,验证降级链路。
>
> 本质上是 **从'人防'转向'技防'** —— 配置错误是人的失误,但'配置错误能导致线上故障'是系统的失误。SRE 的思路是,人的失误不可避免,系统要能容错。"

---

**追问 5**: 如果当时 1 周没定位出来,系统真的被下线,你会怎么办?

**回答**:

> "这个我确实想过 fallback 方案。如果定位不出来,我的计划是:
> 1. **临时回退到旧搜索系统**,保业务可用,但用户体验会降;
> 2. **保留 RAG 系统作为'影子模式'** —— 用户 query 同时走新旧两套,旧系统返回给用户,新系统结果只记录不返回,用来离线分析;
> 3. **用影子模式的数据复现问题** —— 不影响用户的前提下继续排查。
>
> 这个思路的核心是 **'保业务 > 保系统'**。一个不稳定的智能系统比没有智能系统更糟糕,因为它会侵蚀用户信任,而信任一旦失去,后面系统修好了用户也不愿意用。
>
> 当然,最后我们 1 周内定位了,没走到这一步。但这个 fallback 方案我提前和业务方沟通过了,让他们知道'最坏情况是什么',反而稳住了业务方的信心。"

### Q5: 模拟面试 Round 4 — "如果让你重新设计这个系统,你会怎么改进?" + 追问

<details>
<summary>查看答案</summary>

**场景设定**: 二面尾声,面试官想看候选人的架构演进思维和 trade-off 能力。

---

**面试官**: 如果让你重新设计这个企业知识库 Agent,你会怎么改进?

**候选人(分层回答)**:

> "我会从 **架构、检索、Agent、评测** 四个层面改进,按优先级排序:
>
> **短期(1-2 个月,低成本高收益)**:
> 1. **引入 Query Decomposition**: 复杂问题拆子问题,多路召回后合并。预期 Recall@10 从 83% → 88%。
> 2. **从 ReAct 升级到 Plan-and-Execute**: 先规划再执行,减少 LLM 调用次数。预期延迟降 40%。
> 3. **评测集扩到 2000 条 + 分层抽样**: 当前 500 条覆盖不足,扩量后迭代更稳。
>
> **中期(3-6 个月,架构调整)**:
> 4. **多路召回升级**: 加入知识图谱召回(实体+关系),处理'XX 政策依据是什么'这类需要多跳推理的 query。
> 5. **Rerank 升级为两阶段**: 双塔粗排 top-100 + Cross-Encoder 精排 top-10,替代当前 LLM Rerank,延迟降一半且成本降 70%。
> 6. **引入用户画像**: 按角色/部门/历史 query 个性化召回。
>
> **长期(6-12 个月,技术跃迁)**:
> 7. **从 RAG 升级到 Agentic RAG**: Agent 主动决定'要不要检索''检索几次''检索什么',而不是固定流程。
> 8. **自研小模型微调**: 用业务数据微调 7B 模型替代 GPT-4o 的部分场景(比如意图分类、HyDE 生成),成本降 90%。
> 9. **多模态**: 支持图片/PDF 表格的理解,当前只处理文本。"

---

**追问 1**: 你说 Plan-and-Execute 比 ReAct 好,但 Plan-and-Execute 的规划一旦错了,后面全错,怎么处理?

**回答**:

> "这是 Plan-and-Execute 的核心缺陷 —— **规划错误不可恢复**。缓解策略:
> 1. **规划 + 重规划**: 每执行完一步,把结果反馈给 Planner,允许它修改剩余计划。这叫 **Adaptive Planning**。代价是多几次 LLM 调用,但比 ReAct 的每步都调要少。
> 2. **规划置信度**: 让 Planner 输出置信度,低于 0.7 的计划回退到 ReAct 模式(逐步推理)。
> 3. **规划模板库**: 高频任务(请假/报销)用预设规划模板,不走 LLM 规划,避免错误。只有低频/新颖 query 才走 LLM 规划。
> 4. **人工兜底**: 规划失败超 2 次,转人工,并把这条 query 记入'难例集',用于后续优化。
>
> 其实 Plan-and-Execute 和 ReAct 不是二选一,而是 **按任务复杂度路由** —— 简单任务(< 3 步)走 ReAct,复杂任务(> 3 步)走 Plan-and-Execute。这个路由本身可以用一个轻量分类器实现。"

---

**追问 2**: 知识图谱召回你打算怎么落地? 企业知识库构建图谱成本很高吧?

**回答**:

> "成本确实是核心挑战。我的思路是 **轻量图谱 + LLM 抽取**,而不是传统的人工标注图谱:
> 1. **实体抽取**: 用 LLM 从文档里抽实体(政策名/角色/流程/时间),存到 Neo4j。每个文档跑一次,成本可控(50 万文档 × $0.005/篇 = $2500)。
> 2. **关系抽取**: 同样用 LLM,抽'依据''属于''前置条件'等关系。
> 3. **图谱召回**: 用户 query 抽实体 → 图谱查询邻居实体 → 这些实体对应的文档作为召回结果。
> 4. **与向量召回融合**: 图谱召回作为第三路,和向量+BM25 一起走 RRF 融合。
>
> 这个方案的关键是 **不强求图谱完整**,即使只覆盖 30% 的文档,也能提升多跳 query 的召回。我们做过 POC,在'XX 政策的依据是什么'这类 query 上,图谱召回把 Recall 从 45% 提到 72%(向量召回在这类 query 上很差,因为'依据'这种关系不是语义相似能捕捉的)。
>
> 真正的成本不是构建,而是 **维护** —— 文档更新后图谱要同步更新。这个用前面提到的 webhook + 增量重建能解决。"

---

**追问 3**: 自研小模型微调,你有数据吗? 微调的 ROI 怎么算?

**回答**:

> "数据是核心问题。我们的数据来源:
> 1. **HyDE 生成**: 累积了 6 个月的 (query, 假想答案) pair,约 50 万条,可用于微调 HyDE 模型。
> 2. **意图分类**: 累积了 80 万条带意图标签的 query(分类器输出 + 人工纠正),可用于微调意图分类模型。
> 3. **Rerank**: 累积了 20 万条 (query, chunk, 相关性) 三元组(LLM Rerank 输出 + 人工抽检)。
>
> ROI 测算(以 HyDE 为例):
> - GPT-3.5-mini 调用: 8000 query/天 × $0.0005 = $4/天 = $120/月 = $1440/年
> - 微调 Qwen2.5-7B: 标注数据已有(0 成本),训练 1 次 GPU 成本 $50,部署 1 张 A10 月成本 $800
> - **回本周期**: ($50 + $800×12 - $1440) / $1440 ≈ 5.5 个月回本,之后年省 $9000+
>
> 但微调的 **隐性成本** 是模型维护 —— 业务变了要重新微调,评测集要持续更新。所以我的建议是 **只对稳定任务微调**(意图分类),不稳定任务(HyDE)继续用 API。"

---

**追问 4**: 你说 Agentic RAG,这个和普通 RAG 的本质区别是什么?

**回答**:

> "本质区别是 **'谁主导检索'**:
> - **传统 RAG**: 固定流程 —— query → 检索 → 生成。检索是'被动触发'的,不管 query 需不需要。
> - **Agentic RAG**: Agent 主导 —— Agent 判断'这个 query 需要检索吗? 检索什么? 检索结果够不够? 要不要再检索一次?' 检索是 Agent 的'工具',按需调用。
>
> 举个对比:
> - 用户问'你好',传统 RAG 也会去检索(浪费),Agentic RAG 直接回复'你好',跳过检索。
> - 用户问'2024 年年假政策和 2023 年有什么变化',传统 RAG 检索一次(可能只召回 2024 或 2023 的),Agentic RAG 会 **分别检索两次** 再对比。
>
> 实现上,Agentic RAG 就是把'检索'包装成一个 tool,放进 ReAct/Plan-Execute 循环里。难点是 **判断'检索结果够不够'** —— 这需要一个评估模块,我们的做法是用 LLM 判断'当前上下文是否能回答用户问题',不能就再检索。这个判断的准确率直接决定 Agentic RAG 的效果,做不好会要么漏检索(回答不全),要么过度检索(延迟爆炸)。"

---

**追问 5**: 这么多改进点,如果只能做 1 个,你选哪个? 为什么?

**回答**:

> "选 **Query Decomposition**。理由:
> 1. **ROI 最高**: 实现成本低(1 个 LLM 调用 + 多路召回逻辑,2 天开发),收益直接(Recall +5%,覆盖多步问题)。
> 2. **用户感知最强**: 多步问题是当前用户吐槽最多的('我问的是两个政策的对比,你只答了一个'),修复后 NPS 提升明显。
> 3. **不破坏架构**: 不需要换组件、不需要新模型、不需要改数据流,只在 Agent 层加一步 decompose。
> 4. **可回滚**: 如果效果不好,一个 feature flag 关掉就回退,零风险。
>
> 工程上,我有个原则 —— **优先做'可回滚 + 不改架构 + 用户可感'的优化**,这种优化能快速验证、快速产生业务价值,适合作为第一个改进。架构级的改进(比如换 Plan-and-Execute、引入图谱)适合在'低风险优化吃完'之后再做。"

---

**面试官小结**:

这道题是看候选人的 **架构判断力**。差的回答是"全都改"(没有优先级),好的回答是 **"有优先级 + 有 trade-off + 有 ROI 测算"**。最后那个"只做 1 个选哪个"的追问是关键 —— 能选出 ROI 最高且风险最低的,说明真的有架构判断力;选"最酷的"(比如 Agentic RAG),说明还在追新技术,没到工程决策的层次。

### Q6: 项目中的数据飞轮 — 如何在项目中体现数据驱动优化的闭环?

<details>
<summary>查看答案</summary>

**面试官**: 你在项目里怎么搭建数据飞轮的? 数据驱动的闭环长什么样?

**回答**:

> "数据飞轮的核心是 **'数据 → 分析 → 优化 → 上线 → 新数据'** 的闭环。我们项目里的飞轮有 4 个环节:
>
> ```
> ┌─────────────────────────────────────────────────┐
> │                  数据飞轮闭环                      │
> │                                                   │
> │  ① 数据采集 ──→ ② 分析洞察 ──→ ③ 优化迭代       │
> │       ↑                                  ↓        │
> │       └────── ④ 上线验证 ←───── A/B 实验          │
> │                                                   │
> └─────────────────────────────────────────────────┘
> ```

---

**① 数据采集 — 4 类数据全量打点**:

| 数据类型 | 采集内容 | 存储 | 用途 |
|---------|---------|------|------|
| Query 日志 | 原始 query / 时间 / 用户角色 | Kafka → ClickHouse | 挖掘高频 query、新需求 |
| 检索日志 | 召回的 chunk_id / 分数 / 延迟 | ClickHouse | 召回质量分析 |
| 生成日志 | LLM 输出 / 工具调用链 / token 数 | ClickHouse | 生成质量、成本分析 |
| 反馈日志 | 用户点赞/点踩/复问/转人工 | PG | 标注信号、Bad Case |

关键设计: **反馈日志是飞轮的燃料**。我们做了 3 种反馈采集:
- **显式反馈**: 答案下方'有用/没用'按钮,采集率 8%(行业平均 5-10%);
- **隐式反馈**: 用户是否复问(同一意图 5 分钟内再问)、是否转人工、是否复制答案;
- **主动标注**: 每天采样 50 条,内部团队人工标注,作为 golden set。

---

**② 分析洞察 — 周度 Bad Case 归因**:

每周跑一次 Bad Case 分析:
1. 从反馈日志拉'点踩 + 转人工'的 query(每周约 200 条);
2. 用 LLM 做归因分类 —— 是'召回错误'、'生成幻觉'、'理解错误'还是'知识缺失';
3. 对每类做根因分析:
   - **召回错误**: 看 chunk 分块是否合理、query 改写是否出错;
   - **生成幻觉**: 看 prompt 是否给了错误引导、上下文是否足够;
   - **理解错误**: 看 LLM 是否误读了用户意图;
   - **知识缺失**: 文档库里有没有相关内容,没有就推进补录。

归因结果沉淀成一个 **Bad Case 看板**,每周和业务方对齐。

---

**③ 优化迭代 — 3 天一个小版本**:

基于归因,针对性优化:
- 召回错误多 → 调分块策略 / 加 Query 改写规则;
- 生成幻觉多 → 改 prompt / 加约束;
- 知识缺失多 → 推业务方补文档。

迭代节奏: 周一归因 → 周二周三开发 → 周四评测 → 周五上线。**3 天一个迭代**,比传统的 2 周迭代快 5 倍。这个速度的核心是 **评测自动化** —— 500 条评测集跑一遍只要 30 分钟,不需要人工等。

---

**④ 上线验证 — A/B + 护栏**:

每个优化都走 A/B:
- 实验组 10% 流量,对照组 90%;
- 护栏指标: 点踩率不能升、转人工率不能升、P99 延迟不能升;
- 核心指标: 点赞率、召回率、人工评测分;
- 显著性: 至少 7 天 + 样本量 > 5000,才下结论。

实验通过后全量上线,失败的实验做归因,进下一轮飞轮。

---

**追问: 这个飞轮转起来最难的是什么?**

> "最难的是 **反馈采集率**。8% 的显式反馈率看着够用,但其实严重偏向'极度满意'和'极度不满'的用户,中间地带沉默。这导致 Bad Case 归因有 **幸存者偏差**。
>
> 我们的缓解: 重点看 **隐式反馈**(复问率、转人工率),这些是全量数据,无偏差。特别是 **'复问'** —— 用户问了同样的事 5 分钟内再问,大概率是上一次没答好。这个信号比点踩更准,因为点踩需要用户主动操作,复问是自然行为。
>
> 第二个难点是 **归因的准确性**。LLM 归因有时会把'召回错误'误判成'生成幻觉'(因为 LLM 看不到检索过程,只看到结果)。我们后来把 **检索的 chunk 内容也喂给归因 LLM**,让它能区分'没召回到'和'召回了但生成错了',归因准确率从 72% 提到 88%。"

</details>

### Q7: 项目中的 AB 实验 — 如何在面试中讲好一个 AB 实验故事?

<details>
<summary>查看答案</summary>

**面试官**: 说一个你做过的 A/B 实验,从设计到结论。

**回答(结构化讲述)**:

> **实验背景**:
> 我们发现用户对'多文档对比类'query(如'2024 和 2023 年假政策有什么区别')的满意度只有 42%,远低于平均的 78%。分析发现,传统单轮 RAG 只能召回一个版本的文档,无法对比。
>
> **假设**: 引入 Query Decomposition(把复杂问题拆成子问题分别检索),能提升多文档对比类 query 的满意度。
>
> **实验设计**:
>
> | 要素 | 设计 |
> |------|------|
> | 流量分配 | 实验组 10%(开启 Decomposition),对照组 90%(原逻辑) |
> | 实验周期 | 14 天(覆盖两个完整工作周) |
> | 核心指标 | 多文档对比类 query 的点赞率 + 转人工率 |
> | 护栏指标 | 整体 P99 延迟(不能升超过 20%)、整体点踩率(不能升) |
> | 分流方式 | 按 user_id 哈希分流,保证同一用户始终在同一组 |
>
> **实验结果**:
>
> | 指标 | 对照组 | 实验组 | 变化 | 显著性 |
> |------|--------|--------|------|--------|
> | 对比类 query 点赞率 | 42% | 61% | +19pp | p<0.01 |
> | 对比类 query 转人工率 | 28% | 17% | -11pp | p<0.01 |
> | 整体 P99 延迟 | 2.1s | 2.4s | +14% | - |
> | 整体点踩率 | 8.2% | 8.0% | -0.2pp | 不显著 |
>
> **结论**: Decomposition 显著提升对比类 query 体验,且延迟增长 14% 在可接受范围(< 20% 护栏),全量上线。
>
> **意外发现**: 实验组的长 query(>30 字)满意度也涨了 8pp,即使它们不是对比类。分析发现,长 query 往往包含多个子问题,Decomposition 顺带把它们也拆了。这个'意外收益'让我们把 Decomposition 的触发条件从'检测到对比意图'放宽到'query 长度 > 20 字'。
>
> **后续**: 上线后 1 个月,对比类 query 满意度稳定在 58%(比实验时的 61% 略降,因为全量后用户群体更广),但仍远高于基线 42%。

---

**追问 1**: 你怎么判断 14 天的样本量够不够? 实验有没有'偷看'问题?

**回答**:

> "样本量计算: 对比类 query 日均 800 条,实验组 10% = 80 条/天,14 天 = 1120 条。用双边检验,期望效应 5pp,基线 42%,显著性 0.05,功效 0.8,计算所需样本约 600 条/组。我们 1120 条足够。
>
> **偷看问题**: 我们在第 7 天确实看了一次数据(忍不住),实验组已经领先 15pp。但统计上,中途偷看会增加假阳性风险。我们的处理: 第 7 天只看不决策,决策必须等满 14 天。同时用 **序贯检验(Sequential Testing)** 替代固定样本检验,它能允许中途多次查看而不增加假阳性。这个方法是我们从 Google 的 A/B 测试框架学来的。"

---

**追问 2**: 实验组延迟涨了 14%,你为什么觉得可接受?

**回答**:

> "这个 14% 是'多文档对比类 query'的延迟,不是全量 query 的延迟。对比类 query 只占 10% 流量,对整体 P99 影响 1.4%。而整体 P99 的护栏是'不升超过 20%',实际只升了 1.4%,远低于护栏。
>
> 但这里有个 **trade-off 思考**: 我们愿意用 14% 的延迟换 19pp 的满意度提升,是因为对比类 query 是'高价值低频'场景 —— 用户问这种问题往往是做决策(比如选福利方案),对延迟容忍度高,对答案质量敏感。如果是'高频低价值'场景(比如查食堂菜单),14% 的延迟可能就不值得。
>
> 这个判断不能靠技术,要靠 **业务理解**。我们和业务方对齐过,他们认可这个 trade-off。"

---

**追问 3**: 如果实验结果反直觉(比如实验组更差),你会怎么处理?

**回答**:

> "我们真的遇到过。之前做过一个实验,把 Rerank 从 LLM 换成 Cross-Encoder,预期延迟降 50% 且召回率不掉。结果实验组点踩率反而升了 3pp。
>
> 排查发现: Cross-Encoder 的 Rerank 虽然更准,但它 **对长 query 的排序更差**(训练数据偏短 query)。我们的长 query 占 30%,这部分的召回质量下降拖累了整体。
>
> 处理: 实验回滚,改成 **分长度路由** —— 长 query 继续用 LLM Rerank,短 query 用 Cross-Encoder。这个混合方案在后续实验里点踩率持平、延迟降 30%,达到了预期。
>
> 教训: **A/B 实验的'反直觉结果'往往是细分群体的信号**,不能简单地'实验组差就回滚',要下钻看是哪部分用户变差了。'分人群看'是 A/B 分析的基本功。"

---

**讲好 AB 实验故事的 5 个要点**:

1. **背景要具体**: 不是'我们做了个实验',而是'我们发现 X 指标在 Y 场景下是 Z%,原因是...';
2. **假设要明确**: '我们认为做 A 能提升 B',而不是'我们试试看';
3. **设计要严谨**: 流量、周期、指标、护栏、显著性,一个不能少;
4. **结果要量化**: 数字 + 显著性 + trade-off,不是'效果好';
5. **要有意外发现**: 反直觉结果或副产品,体现分析的深度。

**白板题 1: 实现一个 Agent 循环主逻辑**

> 题目: 实现一个最简 ReAct Agent,支持 2 个工具(search 和 calculator),能处理多步推理。要求: 步数上限 8 步,死循环检测,工具失败重试。

**解题思路**:

```
1. 定义 Agent 状态: thought / action / observation / step_count
2. 主循环: while step < max_steps
   - 调 LLM 生成 thought + action
   - 解析 action(tool_name, args)
   - 执行 tool,得 observation
   - 检测死循环(连续相同 action)
   - 如果 LLM 输出 Finish,跳出
3. 错误处理: tool 失败重试 2 次,LLM 输出格式错误重试 1 次
```

**完整实现**:

```python
import json
from typing import Callable

# ---- 工具定义 ----
def search(query: str) -> str:
    """模拟检索工具"""
    if "年假" in query:
        return "年假政策: 入职满1年5天,满3年10天,满5年15天"
    return f"未找到关于'{query}'的文档"

def calculator(expr: str) -> str:
    """模拟计算器"""
    try:
        return str(eval(expr))
    except Exception as e:
        return f"计算错误: {e}"

TOOLS: dict[str, Callable] = {"search": search, "calculator": calculator}
TOOL_DESC = """
可用工具:
- search(query: str): 检索知识库,返回相关文档
- calculator(expr: str): 计算数学表达式

请用以下格式回答:
Thought: <你的思考>
Action: <工具名>
Action Input: <工具参数,JSON格式>
OR
Thought: <你的思考>
Final Answer: <最终答案>
"""

# ---- Agent 主逻辑 ----
class ReActAgent:
    def __init__(self, llm_call: Callable, max_steps: int = 8, max_retry: int = 2):
        self.llm_call = llm_call
        self.max_steps = max_steps
        self.max_retry = max_retry

    def run(self, query: str) -> str:
        history = []
        action_history = []  # 用于死循环检测
        tool_fail_count: dict[str, int] = {}

        for step in range(self.max_steps):
            # 1. 构造 prompt,调 LLM
            prompt = f"{TOOL_DESC}\n\n问题: {query}\n\n历史:\n" + "\n".join(history) + "\n\n请继续:"
            llm_output = self._call_llm_with_retry(prompt)

            # 2. 解析输出
            if "Final Answer:" in llm_output:
                return llm_output.split("Final Answer:")[-1].strip()

            action, action_input = self._parse_action(llm_output)
            if action is None:
                history.append(f"Step {step}: 输出格式错误: {llm_output[:100]}")
                continue

            # 3. 死循环检测: 连续 2 次相同 action
            action_key = (action, action_input)
            if len(action_history) >= 1 and action_history[-1] == action_key:
                history.append(f"Step {step}: 检测到死循环,强制结束")
                return "Agent 陷入死循环,无法回答"
            action_history.append(action_key)

            # 4. 工具禁用检测
            if tool_fail_count.get(action, 0) >= self.max_retry:
                history.append(f"Step {step}: 工具 {action} 已失败 {self.max_retry} 次,禁用")
                continue

            # 5. 执行工具
            tool = TOOLS.get(action)
            if tool is None:
                history.append(f"Step {step}: 未知工具 {action}")
                continue

            try:
                observation = tool(**json.loads(action_input))
                history.append(f"Step {step}: Thought={llm_output[:80]}... Action={action}({action_input}) Observation={observation}")
            except Exception as e:
                tool_fail_count[action] = tool_fail_count.get(action, 0) + 1
                observation = f"工具执行失败({tool_fail_count[action]}/{self.max_retry}): {e}"
                history.append(f"Step {step}: {observation}")

        return f"达到最大步数 {self.max_steps},未能回答。最后状态: {history[-1] if history else '空'}"

    def _call_llm_with_retry(self, prompt: str) -> str:
        for _ in range(self.max_retry + 1):
            try:
                return self.llm_call(prompt)
            except Exception:
                continue
        return "Final Answer: LLM 调用失败"

    def _parse_action(self, output: str) -> tuple[str | None, str]:
        """解析 Action 和 Action Input"""
        try:
            action_line = [l for l in output.split("\n") if l.startswith("Action:")][0]
            input_line = [l for l in output.split("\n") if l.startswith("Action Input:")][0]
            action = action_line.split("Action:")[-1].strip()
            action_input = input_line.split("Action Input:")[-1].strip()
            return action, action_input
        except (IndexError, ValueError):
            return None, None


# ---- 测试 ----
def mock_llm(prompt: str) -> str:
    """模拟 LLM 输出(真实场景替换为 OpenAI/其他 API)"""
    if "历史" not in prompt or len(prompt) < 200:  # 第一步
        return """Thought: 用户问入职2年年假多少天,我需要先查年假政策
Action: search
Action Input: {"query": "年假政策"}"""
    elif "5天" in prompt:  # 第二步,拿到政策后计算
        return """Thought: 政策说满1年5天,用户入职2年,我算一下
Action: calculator
Action Input: {"expr": "5 * 2"}"""
    elif "10" in prompt:  # 第三步,算完了
        return """Thought: 计算 result 是 10,入职2年是10天
Final Answer: 根据年假政策,入职满1年5天,满3年10天。您入职2年,按比例折算约为 5*2=10 天(具体以 HR 系统为准)。"""
    return "Final Answer: 我不知道"

agent = ReActAgent(llm_call=mock_llm)
result = agent.run("我入职2年,年假多少天?")
print(result)
```

**讲解话术**:

> "这道题的核心考点不是'能不能写出来',而是 **'边界处理是否完整'**。我会先在白板上画一个状态机: Start → Thought → Action → Observation → (循环或 Finish)。然后明确告诉面试官我会处理 4 个边界: 步数上限、死循环、工具失败、LLM 输出格式错误。代码里我用 `action_history` 做死循环检测(连续相同 action 就 break),用 `tool_fail_count` 做工具禁用,用 `_parse_action` 做格式容错。
>
> 如果面试官追问'并发执行多个工具',我会把 `tool(**json.loads(action_input))` 改成 `asyncio.gather`,但这需要 LLM 支持'一次输出多个 action',prompt 要改。"

**白板题 2: 流式 JSON 容错解析**

> 题目: LLM 流式输出 JSON,每来一个 token 拼到字符串上。但中间状态可能不是合法 JSON(比如 `'{"name": "张'`)。实现一个 `StreamingJSONParser`,每收到一个 chunk 就尝试解析,返回当前能解析出的部分。

**解题思路**:

```
核心难点: 不完整的 JSON 怎么提取已完整部分?
方案: 尝试解析失败 → 补全缺失的括号/引号 → 再解析
```

**完整实现**:

```python
import json

class StreamingJSONParser:
    """流式 JSON 容错解析器,处理 LLM 流式输出的不完整 JSON"""

    def __init__(self):
        self.buffer = ""

    def feed(self, chunk: str) -> dict | list | None:
        """喂入一个 chunk,返回当前能解析出的部分"""
        self.buffer += chunk
        return self._try_parse()

    def _try_parse(self) -> dict | list | None:
        # 1. 先尝试直接解析
        try:
            return json.loads(self.buffer)
        except json.JSONDecodeError:
            pass

        # 2. 尝试补全: 统计未闭合的括号和引号
        repaired = self._repair_json(self.buffer)
        if repaired is None:
            return None
        try:
            return json.loads(repaired)
        except json.JSONDecodeError:
            return None

    def _repair_json(self, s: str) -> str | None:
        """补全缺失的引号和括号"""
        if not s.strip():
            return None

        # 状态机: 遍历字符,跟踪在字符串内/外、栈深度
        in_string = False
        escape = False
        stack: list[str] = []
        i = 0
        last_complete_key_or_value_end = -1  # 上一个完整 key/value 的结束位置

        while i < len(s):
            c = s[i]
            if in_string:
                if escape:
                    escape = False
                elif c == "\\":
                    escape = True
                elif c == '"':
                    in_string = False
                    last_complete_key_or_value_end = i
            else:
                if c == '"':
                    in_string = True
                elif c in "{[":
                    stack.append(c)
                elif c == "}" and stack and stack[-1] == "{":
                    stack.pop()
                    last_complete_key_or_value_end = i
                elif c == "]" and stack and stack[-1] == "[":
                    stack.pop()
                    last_complete_key_or_value_end = i
                elif c in ",:":
                    last_complete_key_or_value_end = i
            i += 1

        # 如果字符串未闭合,补一个引号
        repaired = s
        if in_string:
            repaired += '"'

        # 如果栈不空,补全括号
        for opener in reversed(stack):
            repaired += "}" if opener == "{" else "]"

        # 如果最后一个 token 是逗号或冒号,截掉(避免解析报错)
        repaired = repaired.rstrip().rstrip(",").rstrip(":")

        return repaired


# ---- 测试 ----
def test_streaming():
    parser = StreamingJSONParser()
    # 模拟 LLM 流式输出: {"name": "张三", "age": 25}
    chunks = ['{', '"na', 'me": ', '"张', '三"', ', "a', 'ge": 2', '5}']
    for chunk in chunks:
        result = parser.feed(chunk)
        print(f"喂入 {chunk!r:15} → {result}")

test_streaming()
```

**输出**:

```
喂入 '{'             → None
喂入 '"na'           → None
喂入 'me": '         → None
喂入 '"张'           → {'name': '张'}
喂入 '三"'           → {'name': '张三'}
喂入 ', "a'          → {'name': '张三'}
喂入 'ge": 2'        → {'name': '张三', 'age': 2}
喂入 '5}'            → {'name': '张三', 'age': 25}
```

**讲解话术**:

> "这道题考的是 **'对 JSON 状态机的理解'**。核心思路是: 不完整的 JSON 不是直接报错,而是 **补全缺失的括号和引号**,让它变成'当前最完整的合法 JSON'。我用一个状态机跟踪'是否在字符串内'和'括号栈',这是处理 JSON 的标准手法。
>
> 一个常见追问是'性能' —— 每次 feed 都全量解析,O(n^2) 复杂度。优化方案是 **增量解析**(只解析新增部分),但实现复杂度高,生产环境可以用 `jsonstream` 库。面试时说清楚 trade-off 即可。"

**白板题 3: 多 Agent 并发编排**

> 题目: 有 3 个 Agent(调研/分析/总结),需要并发执行前 2 个,等它们都完成后把结果喂给第 3 个。要求: 单个 Agent 超时 30s 就用空结果兜底,不能阻塞其他 Agent。

**完整实现**:

```python
import asyncio
from typing import Any

async def research_agent(query: str) -> str:
    """调研 Agent,模拟耗时"""
    await asyncio.sleep(2)
    return f"调研结果: 关于'{query}'找到 3 篇相关文档"

async def analysis_agent(query: str) -> str:
    """分析 Agent,模拟耗时"""
    await asyncio.sleep(3)
    return f"分析结果: '{query}'的核心结论是 X"

async def summary_agent(research: str, analysis: str) -> str:
    """总结 Agent,依赖前两个"""
    await asyncio.sleep(1)
    return f"总结: 结合'{research[:20]}...'和'{analysis[:20]}...',得出最终答案"

async def run_with_timeout(coro, timeout: float = 30, default: str = "") -> str:
    """带超时兜底的协程执行器"""
    try:
        return await asyncio.wait_for(coro, timeout=timeout)
    except asyncio.TimeoutError:
        print(f"  [超时] {coro.__name__} 超过 {timeout}s,用默认值兜底")
        return default

async def orchestrate(query: str) -> str:
    """并发编排: 调研 + 分析 并发,完成后喂给总结"""
    print(f"开始编排,query={query}")

    # 并发执行前两个 Agent
    research_task = run_with_timeout(research_agent(query), timeout=30, default="调研超时,无结果")
    analysis_task = run_with_timeout(analysis_agent(query), timeout=30, default="分析超时,无结果")

    research_result, analysis_result = await asyncio.gather(research_task, analysis_task)
    print(f"  调研完成: {research_result}")
    print(f"  分析完成: {analysis_result}")

    # 喂给总结 Agent
    summary_result = await run_with_timeout(
        summary_agent(research_result, analysis_result),
        timeout=30,
        default="总结超时,返回原始结果"
    )
    print(f"  总结完成: {summary_result}")
    return summary_result

# ---- 测试 ----
async def main():
    result = await orchestrate("AI Agent 的技术趋势")
    print(f"\n最终结果: {result}")

    # 测试超时兜底
    print("\n--- 测试超时 ---")
    async def slow_agent():
        await asyncio.sleep(60)  # 模拟超时
        return "不应该看到这个"
    result = await run_with_timeout(slow_agent(), timeout=1, default="默认兜底值")
    print(f"超时测试结果: {result}")

asyncio.run(main())
```

**讲解话术**:

> "这题考 **asyncio 并发 + 错误处理**。我用 `asyncio.gather` 并发前两个 Agent,用 `asyncio.wait_for` 做超时兜底。关键点是 **'超时不是异常,是用默认值继续'** —— 一个 Agent 挂了不能拖垮整个编排,这是 Agent 系统的韧性设计。
>
> 常见追问: '如果 3 个 Agent 之间有依赖图(不只是线性),怎么做?' 回答用 **拓扑排序 + 每层并发**,或者用现成框架(LangGraph / 自研 DAG 调度)。"

### Q9: 手撕代码题 — 限时 30 分钟手撕"支持流式输出的 RAG Agent"(完整实现 + 讲解话术)

<details>
<summary>查看答案</summary>

**题目**:

> 在 30 分钟内,实现一个支持流式输出的 RAG Agent。要求:
> 1. 接收用户 query,从向量库检索 top-3 相关文档
> 2. 把检索结果拼进 prompt,调用 LLM 流式生成
> 3. 用 SSE(Server-Sent Events)协议把 token 逐个推给客户端
> 4. 如果检索结果为空,直接让 LLM 回答并标注'未找到相关文档'
> 5. 异常处理: LLM 调用失败时返回友好错误,不能崩
>
> 时间限制: 30 分钟(20 分钟编码 + 10 分钟讲解)

**讲解话术(开头 1 分钟)**:

> "我先花 1 分钟讲思路,再 20 分钟写代码,最后讲一遍。
>
> 整体架构是 **检索 + 流式生成 + SSE 推送** 三段:
> 1. **检索层**: 用一个 mock 的向量库(实际替换成 Milvus 客户端),召回 top-3;
> 2. **生成层**: 调 LLM 流式 API(用 mock 模拟 token 逐个返回);
> 3. **传输层**: FastAPI 的 StreamingResponse + SSE 格式。
>
> 关键设计点: **流式不阻塞** —— 检索完后立刻返回 SSE 头,然后边生成边推,客户端体验是'边打字边显示'。异常处理用 try/except 包住每一层,任何一层失败都返回 SSE 错误事件而不是 HTTP 500(因为 SSE 已经开始流了,HTTP 状态码改不了)。
>
> 我用 FastAPI + asyncio 实现,这是 Agent 服务最主流的栈。"

**完整实现(可直接运行)**:

```python
"""
支持流式输出的 RAG Agent
依赖: pip install fastapi uvicorn
运行: uvicorn streaming_rag_agent:app --reload --port 8000
测试: curl -N "http://localhost:8000/chat?query=年假怎么折算"
"""
import asyncio
import json
import random
from typing import AsyncGenerator

from fastapi import FastAPI, Query
from fastapi.responses import StreamingResponse

app = FastAPI()

# ============================================================
# 1. 检索层 (mock 向量库,实际替换为 Milvus/Pinecone 客户端)
# ============================================================
MOCK_DOCUMENTS = [
    {"id": "doc1", "content": "年假政策: 入职满1年享有5天年假,满3年10天,满5年15天。年假按自然年计算,不可跨年累积。"},
    {"id": "doc2", "content": "差旅报销标准: 经济舱机票全额报销,高铁二等座全额报销,住宿一线城市上限500元/晚。"},
    {"id": "doc3", "content": "请假流程: 1天以内直属经理审批,3天以内部门负责人审批,3天以上HR审批。"},
    {"id": "doc4", "content": "报销流程: 登录OA系统提交发票,5个工作日内审批,审批通过后10个工作日打款。"},
]

async def retrieve(query: str, top_k: int = 3) -> list[dict]:
    """模拟向量检索(实际场景: 调用 Milvus 客户端)"""
    await asyncio.sleep(0.1)  # 模拟检索延迟
    # 简单关键词匹配 mock,真实场景用向量相似度
    results = []
    for doc in MOCK_DOCUMENTS:
        score = sum(1 for kw in query if kw in doc["content"]) / max(len(query), 1)
        if any(kw in doc["content"] for kw in query.split()):
            results.append({**doc, "score": 0.8 + random.random() * 0.2})
    return results[:top_k] if results else []

# ============================================================
# 2. 生成层 (mock LLM 流式 API,实际替换为 OpenAI/其他)
# ============================================================
async def llm_stream(prompt: str) -> AsyncGenerator[str, None]:
    """模拟 LLM 流式输出,逐 token yield(实际场景: 调用 OpenAI stream API)"""
    # mock 一段回答,按字逐个吐出
    response = (
        f"根据知识库,回答如下: {prompt[-200:]}\n\n"
        "这是一个流式输出的演示回答,模拟 LLM 逐 token 返回。"
        "在实际场景中,这里会调用 OpenAI 的 stream=True API,每次 yield 一个 token。"
    )
    for char in response:
        await asyncio.sleep(0.02)  # 模拟 LLM 生成延迟(50 token/s)
        yield char

def build_prompt(query: str, contexts: list[dict]) -> str:
    """构造 RAG prompt"""
    if not contexts:
        return (
            f"用户问题: {query}\n\n"
            "未找到相关文档。请基于你的常识回答,并在开头注明'以下回答未经文档验证'。"
        )
    context_text = "\n\n".join(
        f"[文档{i+1}] (score={c['score']:.2f})\n{c['content']}" for i, c in enumerate(contexts)
    )
    return (
        f"你是一个企业知识库助手。请基于以下文档回答用户问题。\n\n"
        f"参考文档:\n{context_text}\n\n"
        f"用户问题: {query}\n\n"
        f"要求: 只基于文档内容回答,不要编造。如果文档无法回答,说明'文档中未提及'。"
    )

# ============================================================
# 3. SSE 流式输出层
# ============================================================
async def sse_stream(query: str) -> AsyncGenerator[str, None]:
    """SSE 格式流式输出"""
    # 事件类型: retrieved(检索完成) / token(逐字) / done(结束) / error(错误)

    # 3.1 检索阶段
    try:
        contexts = await retrieve(query, top_k=3)
        yield _sse_event("retrieved", {
            "count": len(contexts),
            "doc_ids": [c["id"] for c in contexts]
        })
    except Exception as e:
        yield _sse_event("error", {"stage": "retrieve", "message": str(e)})
        yield _sse_event("done", {})
        return

    # 3.2 生成阶段
    prompt = build_prompt(query, contexts)
    try:
        async for token in llm_stream(prompt):
            yield _sse_event("token", {"text": token})
    except Exception as e:
        yield _sse_event("error", {"stage": "generate", "message": str(e)})

    # 3.3 结束
    yield _sse_event("done", {})

def _sse_event(event: str, data: dict) -> str:
    """构造一个 SSE 事件"""
    return f"event: {event}\ndata: {json.dumps(data, ensure_ascii=False)}\n\n"

# ============================================================
# 4. FastAPI 接口
# ============================================================
@app.get("/chat")
async def chat(query: str = Query(..., description="用户问题")):
    """流式聊天接口,返回 SSE 流"""
    return StreamingResponse(
        sse_stream(query),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "Connection": "keep-alive",
            "X-Accel-Buffering": "no",  # 关闭 nginx 缓冲,确保流式
        }
    )

# ============================================================
# 5. 本地测试(不启动服务,直接跑)
# ============================================================
async def test_local():
    print("=== 测试 1: 正常 query ===")
    async for event in sse_stream("年假怎么折算"):
        print(event.strip())

    print("\n=== 测试 2: 检索为空 ===")
    async for event in sse_stream("量子物理原理"):
        print(event.strip())

if __name__ == "__main__":
    asyncio.run(test_local())
```

**讲解话术(代码完成后 5 分钟)**:

> "我讲一下几个关键设计点:
>
> **1. 为什么用 SSE 而不是 WebSocket?**
> SSE 是单向(服务器→客户端),对于'LLM 流式输出'这种场景足够了。WebSocket 是双向,但 LLM 场景客户端只需要发一个 query,之后就是接收,用 WebSocket 过重。而且 SSE 走 HTTP,穿透防火墙、复用 HTTP 基础设施(负载均衡/CDN)更友好。
>
> **2. 为什么用 `event: token` 而不是把所有数据塞一个流?**
> SSE 支持自定义事件类型,我用 `retrieved` / `token` / `done` / `error` 4 种事件,客户端可以 **按类型分别处理** —— 比如 `retrieved` 时显示'已找到 N 篇文档',`token` 时追加文字,`error` 时弹错误提示。这比把所有数据塞一个 JSON 流更清晰。
>
> **3. 错误处理为什么用 SSE error 事件而不是 HTTP 500?**
> 因为 SSE 流开始后(返回 200),后续如果 LLM 挂了,**HTTP 状态码已经改不了了**。如果用 HTTP 500,客户端会以为整个请求失败,丢弃已经收到的 token。用 SSE error 事件,客户端能保留已生成的部分,只在 UI 上标红'生成中断'。这是流式系统的标准做法。
>
> **4. 如果要接真实 LLM,改哪里?**
> 只需要把 `llm_stream` 函数改成调 OpenAI API:
> ```python
> from openai import AsyncOpenAI
> client = AsyncOpenAI()
> async def llm_stream(prompt: str) -> AsyncGenerator[str, None]:
>     stream = await client.chat.completions.create(
>         model="gpt-4o", messages=[{"role": "user", "content": prompt}], stream=True
>     )
>     async for chunk in stream:
>         if chunk.choices[0].delta.content:
>             yield chunk.choices[0].delta.content
> ```
> 接 Milvus 类似,改 `retrieve` 函数即可。**架构不动,只换实现**,这是分层的好处。
>
> **5. 生产环境还需要加什么?**
> - **限流**: token 桶,防止单用户刷接口;
> - **超时**: 整个请求 30s 超时,防止 LLM 卡死;
> - **日志**: 把 query/检索结果/生成内容/延迟全打点,用于飞轮分析;
> - **缓存**: query embedding 近似去重,命中直接回放缓存(但要注意缓存不能流式,只能整体返回);
> - **监控**: P99 延迟、token 速率、错误率,接入 Prometheus。"

**面试官可能的追问**:

**追问 1**: 如果 LLM 流式输出到一半,客户端断开了,服务器怎么感知?

> "FastAPI 的 StreamingResponse 会在客户端断开时抛 `asyncio.CancelledError`,我的 `sse_stream` 协程会被 cancel。这时应该 **释放 LLM 连接**(OpenAI 的 stream 有 `close()` 方法),避免泄漏。生产环境会在 `finally` 块里做清理。
>
> 更进一步,可以监听 `request.is_disconnected()`,主动检测断开,不等 cancel。"

**追问 2**: 多个用户并发请求,你的代码是并行的吗?

> "是并行的。FastAPI + asyncio 是单进程多协程,多个请求的 `sse_stream` 协程会交替执行(asyncio 事件循环调度)。LLM 调用在 `await` 时会让出 CPU,其他请求能跑。
>
> 但有个限制 —— 如果 `retrieve` 或 `llm_stream` 里有 **同步阻塞操作**(比如 `time.sleep` 或同步 HTTP 调用),会阻塞整个事件循环。所以必须用 `asyncio.sleep` 和 `httpx.AsyncClient`。如果有 CPU 密集任务(比如本地 embedding),要用 `asyncio.to_thread` 放到线程池,避免阻塞。"

**追问 3**: 这个接口怎么压测?

> "用 `locust` 或 `wrk`,关注 3 个指标:
> 1. **P99 首字延迟**: 从请求到第一个 `token` 事件的延迟(用户感知的'开始打字');
> 2. **吞吐量**: 每秒能处理的并发流数;
> 3. **错误率**: SSE error 事件的比例。
>
> 压测时要注意 —— 流式接口不能用传统 QPS 衡量,因为一个请求持续 5-10 秒。更合适的指标是 **'并发流数'**(同时活跃的 SSE 连接数),我们的目标是 500 并发流不降级。"

## 易错点提醒(10 个)

1. **项目陈述超过 3 分钟** —— 面试官 60 秒后就开始走神,长篇大论是最常见翻车点。**对策**: 自己录音,砍到 60 秒。

2. **只堆技术栈不讲业务价值** —— "用了 Milvus + GPT-4 + LangChain" 是减分项,"月节省 2400 工时" 才是加分项。**对策**: 每个项目第一句话必须是业务价值。

3. **量化数字说不清怎么测的** —— 说"召回率 83%"但答不出"测试集多大、怎么标注、Recall@几",面试官立刻怀疑数据造假。**对策**: 每个数字准备"测试集来源+标注方式+指标定义"三件套。

4. **技术选型只说优点不说约束** —— "Milvus 开源所以选它" 是低分回答,"在合规+规模+运维三个约束下选 Milvus" 才是高分。**对策**: 永远用"对比三件套"回答选型题。

5. **把多个优化的功劳算到一个技术上** —— "Rerank 让延迟降 60%",但其实 prompt 优化也贡献了一半。面试官一追问就穿帮。**对策**: 主动拆解"这个优化里 X 贡献了 A,Y 贡献了 B"。

6. **回答"重做会怎么改"只会说"加缓存/加机器"** —— 这是初级工程师答案。**对策**: 准备技术层(架构升级)+业务层(流程改进)两层答案,且有优先级。

7. **讲 AB 实验没有护栏指标** —— 只讲核心指标涨了,不提护栏指标是否守住,面试官会问"万一副作用呢"。**对策**: AB 故事必须包含"核心指标+护栏指标+显著性+意外发现"。

8. **白板编程不画状态机直接写代码** —— 写到一半发现漏了边界,推倒重来,时间不够。**对策**: 先在白板左边画状态机/流程图,右边写代码,面试官看到状态机会觉得你思路清晰。

9. **手撕代码不讲解埋头就写** —— 面试官看不到你的思考过程,写得对也不知道你为什么这么写。**对策**: 先 1 分钟讲思路,写完 3 分钟讲设计,全程'边写边说'。

10. **反向提问问"加班多吗/薪资多少"** —— 直接减分。**对策**: 反向提问只问技术/业务/成长,薪资问 HR。

## 自测检查清单

### 概念检查(10 项)

- [ ] 能在 60 秒内讲完一个项目的"业务价值+角色+亮点"?
- [ ] 能说出"5 层追问模型"每一层面试官在考察什么?
- [ ] 能用"决策+实现+量化"三段式讲一个技术细节?
- [ ] 能用"对比三件套"讲一个技术选型(X vs Y vs Z + 约束)?
- [ ] 能用 STAR 讲一个"最难问题"的故事(含数据驱动排查)?
- [ ] 能讲清楚一个 AB 实验的"假设+指标+护栏+结论+意外发现"?
- [ ] 能说出数据飞轮的 4 个环节(采集/分析/优化/验证)?
- [ ] 能说出"重做系统"的 3 层改进(短/中/长期)和优先级?
- [ ] 能说出反向提问的 3 个原则和 3 个万能模板?
- [ ] 能说出 5 个面试讲项目的"易错点"并解释为什么是错的?

### 代码检查(3 项)

- [ ] 能在 20 分钟内手写 ReAct Agent 主逻辑(含死循环检测/工具失败/步数上限)?
- [ ] 能在 15 分钟内手写流式 JSON 容错解析器(含引号/括号补全)?
- [ ] 能在 30 分钟内手撕"支持流式输出的 RAG Agent"(含 SSE/检索/生成/异常处理)?

### 模拟面试检查(5 项)

- [ ] 录音过自己的项目介绍,控制在 60 秒以内?
- [ ] 找朋友做 mock,模拟"10 个连环追问"扛下来不卡壳?
- [ ] 能在白板(或纸上)画 RAG 架构图并讲清每个组件的选型理由?
- [ ] 能在 3 分钟内讲完一个 AB 实验故事(含数字和显著性)?
- [ ] 准备了至少 5 个反向提问问题,且每个都嵌入了"自己的思考"?
