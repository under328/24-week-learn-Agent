### Q1：什么是 LLM Agent？它的核心组件有哪些？⭐⭐⭐⭐⭐

**来源**：字节跳动 Agent 平台（2025.12）、阿里通义实验室、百度文心一言团队

**考点**：Agent 定义、组件拆解、与传统软件 Agent 的区别

<details>
<summary>点击查看参考答案</summary>

#### 一句话定义

LLM Agent 是以大语言模型为核心推理引擎，能够**自主感知环境、规划任务、调用工具、根据反馈调整行动**的智能系统。

#### 核心公式

**Agent = Harness（运行框架）+ Model（模型）**

这个公式来自 AgentGuide，强调 Agent 不等于模型本身。模型只是大脑，Harness 是身体，缺一不可。

#### 四大核心组件

```
┌──────────────────────────────────────────────┐
│                    Agent                      │
│                                              │
│  ┌──────────┐      ┌────────────────────┐    │
│  │   LLM    │      │      Memory        │    │
│  │  (大脑)   │      │  - 短期(上下文窗口) │    │
│  │          │      │  - 长期(向量数据库) │    │
│  └────┬─────┘      │  - 工作记忆         │    │
│       │            └────────────────────┘    │
│  ┌────┴──────┐    ┌────────────────────┐    │
│  │ Planning  │    │      Tools         │    │
│  │ - ReAct   │    │  - 搜索            │    │
│  │ - CoT     │    │  - 代码执行         │    │
│  │ - ToT     │    │  - API 调用        │    │
│  │ - Plan-Exec│   │  - 数据库查询      │    │
│  └───────────┘    └────────────────────┘    │
│                                              │
│  ┌──────────────────────────────────────┐    │
│  │           Agent Loop                 │    │
│  │  感知 → 推理 → 行动 → 观察 → 循环    │    │
│  └──────────────────────────────────────┘    │
└──────────────────────────────────────────────┘
```

| 组件 | 职责 | 常见实现 | 面试追问点 |
|------|------|----------|------------|
| **LLM** | 推理、理解、决策 | GPT-4o、Claude 3.5、DeepSeek-V3 | 模型选择策略：什么场景用什么模型 |
| **Planning** | 任务分解、步骤规划 | ReAct、CoT、ToT、Plan-and-Execute | 不同规划范式的优劣（Day 02 详解） |
| **Memory** | 存储历史和上下文 | Context Window、向量数据库、摘要 | 记忆分层设计（Day 05 详解） |
| **Tools** | 与外部世界交互 | Function Calling、MCP、API | 工具发现与注册机制（Day 03-04 详解） |
| **Agent Loop** | 驱动循环执行 | while 循环 + 终止条件 | 终止条件设计和死循环防护 |

#### 与传统软件 Agent 的区别

面试官可能会追问："Agent 这个概念早就有了，LLM Agent 和传统软件 Agent 有什么区别？"

| 维度 | 传统软件 Agent | LLM Agent |
|------|---------------|-----------|
| 决策方式 | 规则/状态机 | 模型推理 |
| 适应性 | 只能处理预定义场景 | 可处理未见过的场景 |
| 工具调用 | 硬编码 | 自然语言描述即可 |
| 泛化能力 | 无 | 强（但有幻觉风险） |
| 成本 | 低 | 高（token 消耗） |

#### 面试加分点

强调 Agent 的本质不是"能聊天的模型"，而是"能行动的模型"：

- Chatbot 是 `输入 → 输出`
- Agent 是 `输入 → 推理 → 行动 → 观察 → 再推理 → ... → 输出` 的循环

然后引出：正是因为多了"行动"和"循环"，Agent 才有了可靠性、成本、安全等一系列工程挑战。这说明你不只是背了定义，而是理解了为什么 Agent 是一个独立的工程课题。

### Q2：Agent、Chatbot 和 Workflow 有什么区别？什么时候该用 Agent？⭐⭐⭐⭐⭐

**来源**：字节飞书智能助手（2025.10）、阿里达摩院、美团 AI 平台

**考点**：三者边界、工程取舍决策、Anthropic 的 Agent 设计哲学

<details>
<summary>点击查看参考答案</summary>

#### 本质区别：决策的自主性

三者不是"谁比谁好"的关系，而是**自主性递增**的光谱：

```
自主性低 ◄──────────────────────────────► 自主性高

  Chatbot ──────► Workflow ──────► Agent
  (纯对话)       (固定流程)       (动态决策)
  
  无工具          预定义节点       自主选择工具
  单轮交互        固定路径         动态路径
  高可靠性        高可靠性         需额外保障
```

#### 详细对比

| 维度 | Chatbot | Workflow | Agent |
|------|---------|----------|-------|
| 核心模式 | 输入 → 输出 | 固定流程编排 | 动态决策循环 |
| 工具调用 | 无 | 预定义节点 | 自主选择 |
| 路径 | 单轮 | 固定路径 | 动态路径 |
| 自主性 | 无 | 低（人定义流程） | 高（模型决定流程） |
| 可靠性 | 高 | 高 | 较低（需额外保障） |
| 成本 | 低 | 低-中 | 高（多轮 LLM 调用） |
| 可预测性 | 高 | 高 | 低 |
| 适用场景 | 问答、闲聊 | 审批流、ETL、数据处理 | 开放任务、复杂推理、多工具组合 |

#### 什么时候用 Agent

✅ **该用 Agent 的场景**：
- 任务路径不确定，需要根据中间结果动态决策（如"帮我研究一下竞品的定价策略"）
- 需要组合多个工具，且工具选择依赖推理（如先搜索、再分析、再生成报告）
- 用户意图模糊，需要 Agent 自主澄清和探索
- 任务需要多步骤，且每步的结果影响下一步方向

❌ **不该用 Agent 的场景**：
- 任务流程固定 → 用 Workflow，更可靠、更便宜
- 简单问答 → 用 Chatbot，无需工具
- 对可靠性要求极高（如金融交易、医疗诊断）→ 用确定性流程 + Agent 辅助
- 成本敏感的高频场景 → Workflow 的 token 消耗远低于 Agent

#### Anthropic 的 Agent 设计哲学（面试加分）

Anthropic 在其工程博客中明确提出：

> **"不要一上来就建 Agent。先用 Workflow 解决问题，当 Workflow 的分支逻辑复杂到难以维护时，再升级为 Agent。"**

这说明一个重要的工程原则：**Agent 不是目的，而是手段**。很多团队一上来就用 Agent，结果发现不可控、成本高、难以调试。正确的路径是：

```
Chatbot → Workflow → 带条件的 Workflow → 受控 Agent → 自主 Agent
         (先解决)   (加分支)            (有限自主)    (最后才考虑)
```

#### 面试加分点

1. 能引用 Anthropic 的观点，说明你关注行业前沿实践
2. 能举具体例子："比如客服场景，80% 的请求是标准 FAQ，用 Workflow + RAG 就够了。只有 20% 的复杂问题才需要 Agent 介入。一上来全用 Agent 既贵又不可控。"
3. 提到"可预测性"这个维度 —— 在生产环境中，可预测性往往比能力上限更重要

### Q3：详细描述 Agent Loop 的执行过程，终止条件怎么设计？⭐⭐⭐⭐

**来源**：字节 Agent 平台（2025.12）、OpenAI 面经

**考点**：Agent Loop 各阶段理解、终止条件设计、错误恢复

<details>
<summary>点击查看参考答案</summary>

#### Agent Loop 的五个阶段

Agent Loop 是 Agent 的核心运行机制，一个完整的循环包含五个阶段：

```
用户输入: "帮我查一下北京明天的天气，如果下雨就提醒我带伞"
    │
    ▼
┌─ 1. Perception (感知) ──────────────────────┐
│  接收用户输入 + 当前状态 + 历史记忆          │
│  → 理解意图：查天气 + 条件提醒              │
│  → 组装上下文：system prompt + 用户消息      │
│               + 可用工具列表 + 历史对话       │
└──────────────────────┬───────────────────────┘
                       ▼
┌─ 2. Reasoning (推理) ───────────────────────┐
│  LLM 基于上下文进行推理                      │
│  → Thought: 需要先调用天气 API 获取信息      │
│  → Decision: 调用 get_weather(city="北京")  │
│  → 输出：tool_calls（结构化工具调用请求）    │
└──────────────────────┬───────────────────────┘
                       ▼
┌─ 3. Action (行动) ──────────────────────────┐
│  Harness 执行工具调用                       │
│  → 参数校验：city 是字符串，合法            │
│  → 调用：get_weather(city="北京")           │
│  → 返回：{"weather": "rain", "temp": 12}   │
│  → 异常处理：超时/错误时的 fallback         │
└──────────────────────┬───────────────────────┘
                       ▼
┌─ 4. Observation (观察) ─────────────────────┐
│  将工具返回结果注入上下文                    │
│  → messages.append({role: "tool", ...})     │
│  → LLM 分析：明天有雨，需要提醒带伞         │
│  → 判断：任务是否完成？                      │
└──────────────────────┬───────────────────────┘
                       ▼
┌─ 5. Termination Check (终止判断) ───────────┐
│  任务完成？                                  │
│  → 是：LLM 不再输出 tool_calls              │
│       → 生成最终回复并退出循环               │
│  → 否：回到步骤 2 继续推理                   │
│  → 超限？：达到 max_steps → 强制终止        │
└──────────────────────┬───────────────────────┘
                       ▼
输出: "北京明天有小雨，气温12°C，记得带伞！"
```

#### 终止条件设计（面试重点）

终止条件是 Agent Loop 的安全网，生产环境至少要有三层：

| 层级 | 条件 | 作用 | 实现方式 |
|------|------|------|----------|
| **L1 正常终止** | LLM 不再输出 tool_calls | 模型认为任务完成 | `if not msg.tool_calls: break` |
| **L2 步数限制** | 达到 max_steps | 防止死循环 | `for step in range(max_steps)` |
| **L3 超时限制** | 超过时间预算 | 防止卡在某一步 | `timeout` 装饰器 / 异步超时 |
| **L4 成本限制** | token 消耗超预算 | 防止成本失控 | 累计 token 超阈值则终止 |
| **L5 重复检测** | 连续相同的工具调用 | 检测卡死状态 | 记录最近 N 步，检测重复模式 |

#### 错误恢复机制

工具调用失败时，Agent 的处理策略：

```python
def execute_tool_with_recovery(tool_call, max_retries=3):
    for attempt in range(max_retries):
        try:
            result = execute_tool(tool_call)
            return result
        except ToolTimeoutError:
            # 超时：重试或换工具
            if attempt < max_retries - 1:
                continue
            return "工具调用超时，请尝试其他方式"
        except ToolParamError:
            # 参数错误：不重试，直接返回错误让 LLM 调整
            return f"参数错误：{tool_call.function.arguments}"
        except ToolPermissionError:
            # 权限不足：不重试，需要人工介入
            return "权限不足，需要人工确认"
```

关键原则：
- **可重试错误**（超时、限流）→ 自动重试
- **不可重试错误**（参数错、权限不足）→ 将错误信息返回给 LLM，让它自行调整策略
- **不要静默吞掉错误** —— 错误信息对 LLM 是有价值的信号

#### 面试加分点

1. 提到"五层终止条件"而非只说"max_steps"，展示工程深度
2. 提到"错误信息是 LLM 的信号"这个观点 —— 不要吞掉错误，要让 Agent 知道发生了什么
3. 提到"重复检测"这个高级话题：Agent 可能反复调用同一工具同一参数，这是死循环的典型表现。可以通过记录最近 N 步的 (tool_name, args) 哈希来检测

### Q4：什么是 Agent Harness？为什么这个概念在 2026 年成为面试新考点？⭐⭐⭐⭐

**来源**：AgentGuide（2026 前沿考点）、Anthropic 工程博客、OpenHands 文档

**考点**：Harness 定义、职责边界、为什么是生产级 Agent 的核心壁垒

<details>
<summary>点击查看参考答案</summary>

#### 定义

**Harness** 指的是包裹在模型外层的运行时框架，负责管理 Agent 的执行循环、上下文、工具注册、权限控制、错误处理、可观测性等所有"非推理"工作。

用一句话概括：**模型负责想，Harness 负责做。**

#### 架构位置

```
┌─────────────────────────────────────────────┐
│              Agent System                    │
│  ┌───────────────────────────────────────┐  │
│  │             Harness                   │  │
│  │                                       │  │
│  │  ┌────────────┐  ┌─────────────────┐ │  │
│  │  │ Agent Loop │  │ Context Manager │ │  │
│  │  │  驱动循环  │  │  压缩/截断/缓存 │ │  │
│  │  └────────────┘  └─────────────────┘ │  │
│  │  ┌────────────┐  ┌─────────────────┐ │  │
│  │  │ Tool Reg.  │  │  Permission     │ │  │
│  │  │ 注册与调度 │  │  权限/沙箱/HITL │ │  │
│  │  └────────────┘  └─────────────────┘ │  │
│  │  ┌────────────┐  ┌─────────────────┐ │  │
│  │  │   Trace    │  │  Cost Guard     │ │  │
│  │  │ 记录/回放  │  │  预算/限流      │ │  │
│  │  └────────────┘  └─────────────────┘ │  │
│  │  ┌─────────────────────────────────┐ │  │
│  │  │           Model                 │ │  │
│  │  │       (LLM 推理核心)            │ │  │
│  │  └─────────────────────────────────┘ │  │
│  └───────────────────────────────────────┘  │
└─────────────────────────────────────────────┘
```

#### Harness 的六大职责

| 职责 | 说明 | 面试追问点 |
|------|------|------------|
| **Agent Loop 驱动** | 管理感知-推理-行动-观察循环 | 终止条件怎么设计？ |
| **上下文管理** | 窗口压缩、关键信息摘要、Prompt Cache | 什么时候截断？什么时候摘要？ |
| **工具注册与调度** | 工具发现、参数校验、并行/串行调度 | MCP vs Function Calling？ |
| **权限与安全** | 操作确认、沙箱隔离、敏感操作拦截 | HITL 什么时候触发？ |
| **Trace 与可观测性** | 每步推理和工具调用记录、Replay | Trace 格式怎么设计？ |
| **成本控制** | token 预算、模型路由、限流 | 怎么用小模型降本？ |

#### 为什么 2026 年成为面试新考点

1. **行业共识形成**：2025 年大家还在讨论"用什么模型"，2026 年行业意识到"模型差距在缩小，Harness 才是差异化"。同一个 GPT-4o，好的 Harness 能让任务成功率从 40% 提到 80%。
2. **Claude Code / Cursor / OpenHands 的成功**：这些产品的核心不是模型（模型人人能调），而是 Harness 工程 —— 上下文管理、工具编排、错误恢复、权限控制做得极好。
3. **面试筛选信号**：多数候选人只知道"调 API + 接工具"，能讲出 Harness 说明你理解 Agent 系统的工程全貌，而不是只跑过 demo。

#### 具体例子：同一个模型，不同 Harness 的效果差异

```
场景：让 Agent 阅读一个 100 页 PDF 并回答问题

❌ 差的 Harness：
  - 把整个 PDF 塞进 context → 超 token 限制 → 报错
  - 或者只截取前 10 页 → 丢失关键信息 → 答案不准确

✅ 好的 Harness：
  - 自动分块 + 向量化 → 按问题检索相关段落
  - 检索结果做 rerank → 提高相关性
  - 上下文超长时自动压缩历史对话
  - 记录每步 Trace → 答案可溯源
  - 成本监控 → 超预算时降级到小模型
```

#### 面试加分点

1. 能说出"模型是大脑，Harness 是身体"这个比喻
2. 能举具体产品例子（Claude Code、Cursor、OpenHands）
3. 能讲出 Harness 六大职责中至少三个的具体实现细节
4. 引出结论："生产级 Agent 的壁垒在 Harness，不在模型。模型人人都能调，但上下文工程、错误恢复、权限管理这些工程能力是差异化的。"

</details>

### Q5：Agent 的可靠性有哪些常见问题？如何系统性解决？⭐⭐⭐⭐

**来源**：字节安全与治理（2026.02）、蚂蚁集团、美团

**考点**：可靠性问题的系统性分类、工程对策、Guardrails 设计

<details>
<summary>点击查看参考答案</summary>

#### 六大常见可靠性问题

| 问题 | 表现 | 根因 | 危害等级 |
|------|------|------|----------|
| **死循环** | Agent 反复调用同一工具，无法前进 | LLM 丢失上下文 / 工具返回不明确 | 高 |
| **幻觉工具调用** | 调用不存在的函数或参数错误 | LLM 编造函数名 / 参数类型不匹配 | 高 |
| **上下文丢失** | 长任务中遗忘早期关键信息 | 上下文窗口有限 / 截断策略不当 | 中 |
| **错误传播** | 一步错步步错 | 中间结果未校验 / 无自我纠错 | 高 |
| **成本失控** | 大量 token 消耗 | 无预算限制 / 模型选择不当 | 中 |
| **安全风险** | 被注入恶意指令 | 输入未过滤 / 权限未分级 | 严重 |

#### 系统性解决方案：四层防御

```
┌─────────────────────────────────────────────┐
│             L4 沙箱与隔离                    │
│  代码执行在隔离容器 / 限制网络和文件系统     │
├─────────────────────────────────────────────┤
│             L3 Human-in-the-Loop            │
│  高风险操作 → 人工确认后才执行               │
├─────────────────────────────────────────────┤
│             L2 Guardrails (守卫层)          │
│  输入端：意图安全检查 / 注入检测            │
│  输出端：工具合法性校验 / 内容安全过滤      │
├─────────────────────────────────────────────┤
│             L1 Loop 安全网                  │
│  max_steps / 超时 / 成本预算 / 重复检测     │
└─────────────────────────────────────────────┘
```

**L1 - Loop 安全网（必备）**：
```python
for step in range(max_steps):
    if total_tokens > budget_limit:
        return "成本超限，终止"
    if detect_repetition(recent_steps, window=3):
        return "检测到死循环，终止"
    # ... agent loop ...
```

**L2 - Guardrails（守卫层）**：

输入守卫 —— 在用户输入到达 LLM 之前检查：
- Prompt Injection 检测（如"忽略之前的指令"）
- 敏感信息脱敏（手机号、身份证号）
- 意图安全分类（是否包含恶意请求）

输出守卫 —— 在 LLM 输出工具调用之前校验：
- 工具名是否在注册表中
- 参数类型是否匹配 Schema
- 操作风险等级评估（高危操作触发 HITL）

**2026 新趋势**：用决策模型（如 Jev/Laya）做毫秒级守卫。传统方式用 LLM 做守卫又贵又慢，决策模型一次前向传播返回校准概率，成本是 LLM judge 的千分之一，延迟从秒级降到毫秒级。

**L3 - HITL（人工确认）**：

哪些操作需要人工确认？

| 风险等级 | 操作类型 | 处理方式 |
|---------|---------|---------|
| 低 | 搜索、查询 | 自动执行 |
| 中 | 发送邮件、修改配置 | 提示用户确认 |
| 高 | 删除数据、转账 | 必须人工审批 |

**L4 - 沙箱执行**：
- 代码执行工具在 Docker 容器中运行
- 限制网络访问（白名单）
- 限制文件系统访问（只允许临时目录）
- 限制执行时间

#### 面试加分点

1. 强调"不要指望模型自己可靠，可靠性是工程手段保障出来的"
2. 能说出四层防御的层级关系，而不是零散列举
3. 提到决策模型做守卫这个新趋势（Jev/Laya），展示前沿认知
4. 举具体例子："比如在 RAG Agent 中，检索结果可能不相关。可以在 Agent 调用 LLM 之前加一个相关性判断守卫，低于阈值就触发重新检索或降级回答。"

</details>

### Q6：如何评估一个 Agent 的效果？评估框架有哪些？⭐⭐⭐⭐

**来源**：字节 Agent 平台（2025.12）、阿里通义、OpenAI

**考点**：多维评估体系、过程 vs 结果、评估工具选型

<details>
<summary>点击查看参考答案</summary>

#### 为什么 Agent 评估难

传统 ML 评估：输入 → 输出 → 对比标签，二元判断。

Agent 评估难在：
1. **路径不唯一**：同一个任务，Agent 可以走不同路径完成，不能只看最终结果
2. **过程重要**：一个 3 步完成的 Agent 比 20 步完成的 Agent 好，即使结果一样
3. **非确定性**：同一个输入，Agent 每次走的路径可能不同
4. **多维度**：成功率、效率、成本、安全都要看

#### 五维评估体系

```
评估维度
│
├── 1. 任务成功率 (Task Success Rate)
│   ├── 最终输出是否完成了用户目标
│   ├── 细粒度：完全成功 / 部分成功 / 失败
│   └── 方法：人工标注 or LLM-as-Judge
│
├── 2. 过程质量 (Process Quality)
│   ├── 工具选择准确率：是否选了正确的工具
│   ├── 工具调用参数正确率：参数是否准确
│   ├── 路径效率：实际步数 / 最短步数
│   └── 错误恢复率：出错后能否自行纠正
│
├── 3. 效率指标 (Efficiency)
│   ├── 平均步数：完成任务用了几轮循环
│   ├── 平均 token 消耗（输入 + 输出）
│   ├── 端到端延迟 (p50 / p95 / p99)
│   └── 单次任务成本（美元）
│
├── 4. 安全性 (Safety)
│   ├── 越狱攻击抵御率
│   ├── 提示注入防御率
│   ├── 敏感信息泄露率
│   └── 权限越界率
│
└── 5. 用户体验 (UX)
    ├── 回答相关性
    ├── 回答完整性
    ├── 回答延迟感受
    └── 用户满意度评分
```

#### 评估方法对比

| 方法 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|---------|
| **人工标注** | 人工评估 Agent 输出 | 最准确 | 慢、贵 | 小规模基准测试 |
| **LLM-as-Judge** | 用更强的模型做裁判 | 可扩展 | 贵、有方差（GPT vs Claude 判断不一致） | 大规模离线评测 |
| **决策模型评测** | 用 Jev/Laya 做类型化判断 | 毫秒级、分厘级、方差小 | 只能判断类型化问题 | 守卫、在线评测 |
| **规则匹配** | 正则/关键词匹配 | 快、免费 | 覆盖面窄 | 简单任务 |
| **在线 A/B** | 生产环境分流对比 | 真实用户反馈 | 周期长 | 上线后验证 |

**LLM-as-Judge 的方差问题**（面试重点）：

LangChain 实测数据：在相同 trace 上，GPT 和 Claude judge 的分数方差是 Jev 决策模型的 **92x ~ 913x**。一个自己都改变主意的裁判，做不了可靠的测试套件。

这就是为什么 2026 年趋势是用决策模型替代 LLM judge 做 Agent 评测。

#### 常用评估框架

| 框架 | 特点 | 适用场景 |
|------|------|---------|
| **RAGAS** | RAG 专项评测（faithfulness、relevancy） | RAG Agent |
| **DeepEval** | 类似单元测试的 Agent 评测 | 开发阶段 |
| **Promptfoo** | Prompt/Agent 批量测试 | 回归测试 |
| **Inspect** | 安全与能力评测 | 红队测试 |
| **jevals** | 基于 Jev 决策模型的 Agent eval | 在线评测、守卫 |
| **WebArena / OSWorld** | Web/OS 交互 Agent 基准 | 研究 |
| **SWE-bench** | 代码修复 Agent 基准 | Coding Agent |

#### 面试加分点

1. 强调"过程比结果重要" —— 评估要看路径效率，不能只看成功率
2. 能说出 LLM-as-Judge 的方差问题及决策模型替代方案
3. 提出评估应该分层：离线评测（开发期）→ 在线评测（上线后）→ 用户反馈（持续改进）
4. 引出 Trace/Replay 的重要性：没有 Trace 就无法做过程评估

</details>

### Q7：Agent 的成本怎么控制？有哪些具体手段？⭐⭐⭐

**来源**：美团 AI 平台、字节飞书、阿里钉钉

**考点**：成本拆解、模型路由、上下文优化、Prompt Cache

<details>
<summary>点击查看参考答案</summary>

#### 成本拆解

Agent 的成本主要来自三部分：

```
总成本 = LLM 调用成本 + 工具执行成本 + 基础设施成本

其中 LLM 调用成本通常占 80%+，是优化重点。

LLM 调用成本 = Σ (输入token数 × 输入价格 + 输出token数 × 输出价格) × 调用次数
```

#### 六大成本控制手段

**1. 模型路由（Model Routing）**

不同复杂度的任务用不同模型：

```
用户输入
    │
    ▼
┌─ 路由判断 ──────────────┐
│  简单意图 → 小模型      │  GPT-4o-mini / DeepSeek-V3
│  复杂推理 → 大模型      │  GPT-4o / Claude 3.5
│  代码生成 → 代码模型    │  DeepSeek-Coder
└─────────────────────────┘
```

路由判断可以用决策模型（如 Laya，10ms 级、几乎免费），也可以用规则。

实际效果：某客服 Agent 把 70% 请求路由到小模型，成本降低 60%+，准确率只降 2%。

**2. Prompt Cache（提示缓存）**

Anthropic 和 OpenAI 都支持 Prompt Cache：如果多次请求的 system prompt 和前缀相同，缓存部分可以不重复计费。

- Anthropic：缓存命中部分价格降 90%
- OpenAI：缓存命中部分价格降 50%

对 Agent 来说，system prompt + 工具定义 + 少量示例通常在每次调用中相同，缓存收益巨大。

**3. 上下文压缩**

长对话不要无限堆积，定期做摘要：

```python
def manage_context(messages, max_tokens=8000):
    total = count_tokens(messages)
    if total <= max_tokens:
        return messages
    
    # 保留最近 N 轮 + 系统提示
    system = messages[0]
    recent = messages[-6:]
    
    # 中间部分做摘要
    middle = messages[1:-6]
    summary = summarize(middle)  # 用小模型做摘要
    
    return [system, {"role": "system", "content": f"历史摘要：{summary}"}] + recent
```

**4. 并行工具调用**

OpenAI 支持一次返回多个 tool_calls。如果工具之间无依赖，并行执行可以减少循环次数，从而减少 LLM 调用次数。

```python
# 串行：3 步 = 3 次 LLM 调用
step1 → step2 → step3

# 并行：1 步 = 1 次 LLM 调用
step1 + step2 + step3（同时执行）
```

**5. 结果缓存**

相同或相似的查询，直接返回缓存结果，不走 Agent：

```python
cache_key = hash(user_query)
if cache_key in result_cache:
    return result_cache[cache_key]
# ... agent 执行 ...
result_cache[cache_key] = result
```

**6. 步数预算**

不只是 token 预算，还要控制步数。每多一步循环，就多一次 LLM 调用：

```python
MAX_STEPS = 10  # 硬限制
SOFT_STEPS = 7  # 软限制：超过后提示 Agent 尽快收尾
```

#### 成本估算示例

```
场景：客服 Agent，日均 10 万次对话

优化前（全用 GPT-4o）：
  每次对话平均 5 轮 × 2000 token × $0.005/1K = $0.05/次
  日成本：10万 × $0.05 = $5,000/天

优化后（模型路由 + Prompt Cache + 上下文压缩）：
  70% 用 mini：5轮 × 2000 token × $0.0003/1K = $0.003/次
  30% 用 4o：  5轮 × 1500 token × $0.005/1K × 70%(cache) = $0.005/次
  日成本：7万 × $0.003 + 3万 × $0.005 = $360/天
  降幅：92.8%
```

#### 面试加分点

1. 能拆解成本结构，而不是只说"用便宜的模型"
2. 能给出量化的成本估算（如上面的例子）
3. 提到 Prompt Cache，这是 2025-2026 的新能力，很多候选人不知道
4. 强调成本控制不是一味用小模型，而是"对的任务用对的模型"

</details>

### Q8：手写一个最小的 Agent Loop（Python）⭐⭐⭐⭐⭐

**来源**：字节 Agent 平台（2025.12）、阿里 coding 面、OpenAI

**题目**：不使用任何框架，用 OpenAI SDK 手写一个最简 ReAct Agent，能调用工具、循环执行、自行判断终止。要求包含错误处理和死循环检测。

<details>
<summary>点击查看参考答案</summary>

#### 完整实现

```python
import json
import openai

# ========== 1. 工具函数定义 ==========

def get_weather(city: str) -> str:
    """模拟天气查询"""
    weather_db = {"北京": "晴 15°C", "上海": "雨 20°C", "深圳": "多云 28°C"}
    return weather_db.get(city, f"{city}：暂无天气数据")

def calculate(expression: str) -> str:
    """安全计算器（只允许数字和基本运算符）"""
    try:
        allowed = set("0123456789+-*/(). ")
        if all(c in allowed for c in expression):
            return str(eval(expression))
        return "错误：包含不允许的字符"
    except ZeroDivisionError:
        return "错误：除以零"
    except (SyntaxError, NameError):
        return "错误：表达式无效"

# ========== 2. 工具注册表（OpenAI function calling 格式）==========

TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "查询指定城市的天气",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {"type": "string", "description": "城市名称"}
                },
                "required": ["city"]
            }
        }
    },
    {
        "type": "function",
        "function": {
            "name": "calculate",
            "description": "数学表达式计算",
            "parameters": {
                "type": "object",
                "properties": {
                    "expression": {"type": "string", "description": "数学表达式，如 2+3*4"}
                },
                "required": ["expression"]
            }
        }
    }
]

TOOL_MAP = {
    "get_weather": get_weather,
    "calculate": calculate,
}

# ========== 3. Agent Loop 核心实现 ==========

def run_agent(
    user_query: str,
    max_steps: int = 10,
    verbose: bool = True,
) -> str:
    """
    最简 ReAct Agent Loop
    
    参数:
        user_query: 用户问题
        max_steps: 最大循环次数（防死循环）
        verbose: 是否打印每步日志
    
    返回:
        Agent 最终回复
    """
    messages = [
        {
            "role": "system",
            "content": (
                "你是一个有用的助手，可以调用工具来回答问题。"
                "当你可以直接回答时，不需要调用工具。"
                "完成任务后直接给出最终回答。"
            ),
        },
        {"role": "user", "content": user_query},
    ]

    # 死循环检测：记录最近的工具调用
    recent_calls = []

    for step in range(max_steps):
        if verbose:
            print(f"\n--- Step {step + 1}/{max_steps} ---")

        # --- 感知 + 推理：调用 LLM ---
        try:
            response = openai.chat.completions.create(
                model="gpt-4o",
                messages=messages,
                tools=TOOLS,
                tool_choice="auto",
            )
        except openai.APIError as e:
            return f"LLM 调用失败：{e}"

        msg = response.choices[0].message
        messages.append(msg)

        # --- 终止判断：没有工具调用 → 任务完成 ---
        if not msg.tool_calls:
            if verbose:
                print(f"Agent 最终回复: {msg.content}")
            return msg.content

        # --- 行动：执行工具调用 ---
        for tool_call in msg.tool_calls:
            func_name = tool_call.function.name
            func_args = json.loads(tool_call.function.arguments)

            if verbose:
                print(f"调用工具: {func_name}({func_args})")

            # 死循环检测：连续 3 次相同调用
            call_sig = (func_name, json.dumps(func_args, sort_keys=True))
            recent_calls.append(call_sig)
            if len(recent_calls) >= 3 and len(set(recent_calls[-3:])) == 1:
                if verbose:
                    print("检测到死循环，强制终止")
                return "检测到重复操作，Agent 可能陷入了循环。"

            # 执行工具（带错误处理）
            if func_name in TOOL_MAP:
                try:
                    result = TOOL_MAP[func_name](**func_args)
                except (TypeError, ValueError) as e:
                    result = f"工具执行错误：{type(e).__name__}: {e}"
            else:
                result = f"错误：未知工具 '{func_name}'，可用工具：{list(TOOL_MAP.keys())}"

            if verbose:
                print(f"工具返回: {result}")

            # --- 观察：将结果注入上下文 ---
            messages.append({
                "role": "tool",
                "tool_call_id": tool_call.id,
                "content": result,
            })

    return "达到最大步数限制，Agent 未能完成任务。"


# ========== 4. 运行示例 ==========

if __name__ == "__main__":
    # 示例 1：单工具调用
    print("=" * 50)
    print("示例 1：查天气")
    print("=" * 50)
    run_agent("北京今天天气怎么样？")

    # 示例 2：多步骤推理（需要调用多个工具）
    print("\n" + "=" * 50)
    print("示例 2：多步推理")
    print("=" * 50)
    run_agent("北京和上海哪个温度更高？高多少度？")

    # 示例 3：无需工具
    print("\n" + "=" * 50)
    print("示例 3：直接回答")
    print("=" * 50)
    run_agent("什么是人工智能？")
```

#### 面试追问链

**Q：为什么要设 `max_steps`？**
A：防止 Agent 陷入死循环。生产环境中 Agent 可能反复调用同一工具无法前进，`max_steps` 是最后的安全网。通常设 10-20 步。

**Q：`tool_choice="auto"` 是什么意思？**
A：让 LLM 自主决定是否调用工具以及调用哪个。其他选项：`"none"`（不调工具）、`"required"`（必须调工具）、`{"function": {"name": "xxx"}}`（指定调某个函数）。

**Q：多个 tool_calls 怎么处理？**
A：OpenAI 支持一次返回多个工具调用（并行）。代码中用 for 循环依次执行。生产环境无依赖时可用 `asyncio.gather` 并行执行，减少总延迟。

**Q：这个实现有什么缺陷？如何改进？**
A：
1. ❌ 没有上下文管理 → 长任务会超 token 限制 → 加上下文压缩
2. ❌ 没有 Trace 记录 → 无法回放调试 → 加 Trace logging
3. ❌ 没有权限控制 → 高危操作无保护 → 加 HITL 确认
4. ❌ 没有成本监控 → 可能成本失控 → 加 token 预算
5. ❌ 没有重试机制 → API 失败直接退出 → 加指数退避重试
6. ❌ 死循环检测太简单 → 只检测连续相同 → 可加入语义相似度检测

这些缺陷正是 Harness 要解决的问题。

**Q：如果要支持流式输出怎么改？**
A：把 `create` 换成 `create(stream=True)`，然后迭代 `response` 流。注意流式模式下 `tool_calls` 是分片返回的，需要累积拼接 delta 后再解析。

</details>

### Q9：设计一个智能客服 Agent 系统 ⭐⭐⭐⭐

**来源**：字节飞书智能助手（2025.10）、阿里钉钉 AI、腾讯企点

**题目**：请你设计一个企业级智能客服 Agent，日均 10 万次对话，能处理用户咨询、查询订单、推荐商品、转人工。要求考虑可靠性、成本和可观测性。

<details>
<summary>点击查看参考答案</summary>

#### 整体架构

```
用户消息
    │
    ▼
┌─ 输入守卫 (Guard) ────────────────────────────┐
│  - Prompt Injection 检测                      │
│  - 敏感信息脱敏                               │
│  - 情绪检测（愤怒 → 优先转人工）              │
└──────────────────┬───────────────────────────┘
                   ▼
┌─ 意图路由 (Router) ───────────────────────────┐
│  意图分类（用决策模型，10ms 级）：             │
│  ├── 售前咨询 → 知识库 RAG（L1，60%）         │
│  ├── 售后问题 → 查订单/物流（L2，25%）        │
│  ├── 投诉建议 → 情绪安抚 + 转人工（L3，10%）  │
│  └── 闲聊     → 直接回复（L1，5%）            │
└──────────────────┬───────────────────────────┘
                   ▼
┌─ Agent 核心 (LangGraph 状态图) ────────────────┐
│                                               │
│  ┌─────────┐     ┌──────────────────────┐    │
│  │ Router  │────→│ 知识库 RAG 节点       │    │
│  │ (路由)  │     │ (向量检索 + rerank)   │    │
│  │         │────→│ 订单查询节点          │    │
│  │         │     │ (调用订单 API)        │    │
│  │         │────→│ 商品推荐节点          │    │
│  │         │     │ (用户画像 + 推荐)     │    │
│  │         │────→│ 转人工节点            │    │
│  └─────────┘     └──────────────────────┘    │
│                                               │
│  每个节点执行后 → 质量检查 → 决定下一步       │
└──────────────────┬────────────────────────────┘
                   ▼
┌─ 输出守卫 (Guard) ────────────────────────────┐
│  - 敏感词过滤                                 │
│  - 回复相关性检查（低于阈值 → 重新生成）      │
│  - 引用溯源（标注信息来源）                   │
└──────────────────┬───────────────────────────┘
                   ▼
┌─ Trace 记录 ──────────────────────────────────┐
│  记录：意图、工具调用、检索结果、回复、延迟   │
│  用途：离线分析、问题定位、模型改进           │
└──────────────────┬───────────────────────────┘
                   ▼
               回复用户
```

#### 设计要点详解

**1. 为什么用状态图（LangGraph）而非自由 Agent Loop**

客服场景需要可控性：
- 状态图限制 Agent 只走预定义路径，避免幻觉
- 每条路径可以独立测试、独立优化
- 体现"Workflow 优先，Agent 补充"原则

**2. 分层架构（L1/L2/L3）**

| 层级 | 场景 | 处理方式 | 成本 |
|------|------|---------|------|
| L1 | 标准 FAQ、闲聊 | RAG 直答，不走 Agent | 极低 |
| L2 | 需要多步推理 | Agent 处理（查订单+分析） | 中 |
| L3 | 投诉/复杂/高风险 | 转人工 | 人工成本 |

**3. 记忆设计**

```
短期记忆：当前会话上下文（最近 10 轮对话）
    → 存在 Redis，TTL 30 分钟

长期记忆：用户画像（购买历史、偏好、投诉记录）
    → 存在向量数据库，按 user_id 检索

工作记忆：当前任务的关键信息（如订单号、商品 ID）
    → 存在 LangGraph State 中，任务结束即清除
```

**4. 成本控制策略**

```
模型路由：
  - L1 意图分类 → 决策模型（Laya，几乎免费）
  - L1 FAQ 回复 → 小模型（GPT-4o-mini，$0.3/1M token）
  - L2 Agent 推理 → 大模型（GPT-4o，$5/1M token）
  - 70% 请求走 L1 → 总成本降 60%+

Prompt Cache：
  - system prompt + 工具定义固定 → 缓存命中降 50-90%
```

**5. 可观测性**

每条对话记录 Trace，字段包括：
```json
{
  "trace_id": "xxx",
  "timestamp": "2026-09-22T10:00:00Z",
  "user_id": "xxx",
  "intent": "售后查询",
  "path": ["router", "order_query", "response"],
  "tool_calls": [{"name": "get_order", "args": {"order_id": "123"}, "result": "..."}],
  "rag_results": [{"doc": "...", "score": 0.92}],
  "model_used": "gpt-4o-mini",
  "tokens": {"input": 1200, "output": 300},
  "latency_ms": 850,
  "cost_usd": 0.002,
  "guard_results": {"input_safe": true, "output_relevant": true}
}
```

**6. 错误恢复**

- RAG 检索无结果 → 降级为通用回复 + 推荐转人工
- 订单 API 超时 → 告知用户"系统繁忙" + 记录待处理
- LLM 生成失败 → 重试 1 次，仍失败则转人工

#### 面试加分点

1. **分层架构**：不是一上来全用 Agent，而是 L1/L2/L3 分层，体现工程取舍
2. **量化估算**：能给出"70% 走 L1，成本降 60%"这类数据
3. **可观测性**：Trace 的具体字段设计，说明你做过生产系统
4. **错误恢复**：每个节点的 fallback 策略，而不是只讲 happy path

</details>

### Q10：Agent 和传统 RPA / 规则引擎有什么区别？各自适合什么场景？⭐⭐⭐

**来源**：蚂蚁集团、美团、字节国际化

**考点**：技术演进认知、场景选型能力、不盲目追热点

<details>
<summary>点击查看参考答案</summary>

#### 三者对比

| 维度 | 规则引擎 | RPA (机器人流程自动化) | LLM Agent |
|------|---------|----------------------|-----------|
| 决策方式 | 预定义规则（if-else） | 录制/编写的固定操作脚本 | LLM 推理决策 |
| 适应性 | 只能处理规则覆盖的场景 | 只能处理录制过的 UI 流程 | 可处理未见过的场景 |
| 开发方式 | 配置规则 | 录制/编写脚本 | 自然语言描述工具 |
| 维护成本 | 规则爆炸后难维护 | UI 变化即失效 | 需调优 prompt 和工具 |
| 可靠性 | 极高 | 高（UI 不变时） | 较低（需工程保障） |
| 成本 | 极低 | 低 | 高（token 消耗） |
| 典型产品 | Drools、Easy Rules | UiPath、Automation Anywhere | LangGraph、AutoGen |

#### 各自适合的场景

**规则引擎适合**：
- 业务规则明确且稳定（如风控规则、定价规则）
- 要求 100% 可解释性（合规要求）
- 决策路径固定，不需要"理解"和"推理"

**RPA 适合**：
- 跨系统的重复性操作（如从 A 系统复制数据到 B 系统）
- 操作对象是 UI（没有 API 可用）
- 流程固定且低频变化

**LLM Agent 适合**：
- 任务需要理解和推理（如"分析这份报告的核心风险"）
- 工具组合方式不确定（需要根据情况选择不同工具）
- 用户意图模糊，需要澄清和探索
- 非结构化数据处理（自然语言、图片、代码）

#### 混合架构（面试加分）

生产环境中，三者不是互斥的，而是**分层协作**：

```
┌─────────────────────────────────────────┐
│  LLM Agent 层                           │
│  - 理解用户意图                         │
│  - 规划任务步骤                         │
│  - 处理非结构化输入                     │
├─────────────────────────────────────────┤
│  规则引擎层                             │
│  - 执行明确的业务规则                   │
│  - 风控/合规检查                        │
│  - 定价/折扣计算                        │
├─────────────────────────────────────────┤
│  RPA 层                                 │
│  - 操作没有 API 的遗留系统              │
│  - 跨系统数据搬运                       │
└─────────────────────────────────────────┘

例子：用户说"帮我处理这批退款"
  → Agent 理解意图，规划步骤
  → 规则引擎判断退款是否符合政策
  → RPA 在遗留 ERP 系统中执行退款操作
```

#### 面试加分点

1. 不贬低传统技术 —— 规则引擎和 RPA 在各自领域依然是最优解
2. 能说出"混合架构"的思路 —— Agent 做大脑，规则引擎做骨架，RPA 做手脚
3. 举具体例子说明什么时候不该用 Agent："如果一个审批流程有 5 个固定节点，用规则引擎 10 分钟就能配好，用 Agent 反而不可控还贵。"

</details>

### 面试速记卡（口述练习用）

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

问：什么是 Agent？
答：以 LLM 为大脑，能自主感知-推理-行动-观察循环的智能系统。
    四大组件：LLM + Planning + Memory + Tools。
    核心区别：Chatbot 是输入→输出，Agent 是输入→循环→输出。
    公式：Agent = Harness + Model。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

问：Agent 和 Workflow 怎么选？
答：流程固定用 Workflow，路径不确定用 Agent。
    优先 Workflow，分支复杂到难维护时再升级 Agent。
    Anthropic 原话："不要一上来就建 Agent。"
    实际路径：Chatbot → Workflow → 带条件 Workflow → 受控 Agent → 自主 Agent

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

问：Agent Loop 怎么终止？
答：五层终止条件——
    1. LLM 不再输出 tool_calls（正常终止）
    2. 达到 max_steps（防死循环）
    3. 超时限制（防卡死）
    4. 成本预算超限（防失控）
    5. 重复检测（连续相同调用 → 强制终止）

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

问：什么是 Harness？为什么重要？
答：包裹模型的运行时框架，管理循环/上下文/工具/权限/Trace/成本。
    模型负责想，Harness 负责做。
    生产级 Agent 的壁垒在 Harness，不在模型。
    例子：Claude Code、Cursor、OpenHands 的核心都是 Harness 工程。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

问：Agent 可靠性怎么保障？
答：四层防御——
    L1 Loop 安全网：max_steps / 超时 / 成本预算 / 重复检测
    L2 Guardrails：输入端注入检测 + 输出端工具校验
    L3 HITL：高风险操作人工确认
    L4 沙箱：代码执行隔离，限制网络和文件系统
    核心原则：不要指望模型自己可靠，可靠性是工程手段保障出来的。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

问：Agent 成本怎么控制？
答：六大手段——
    1. 模型路由：简单用小模型，复杂用大模型（省 60%+）
    2. Prompt Cache：固定前缀缓存命中降 50-90%
    3. 上下文压缩：长对话做摘要，不无限堆积
    4. 并行工具调用：无依赖的工具并行执行
    5. 结果缓存：相同查询直接返回
    6. 步数预算：控制最大循环次数

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 易错点提醒
