# 经典项目故事(STAR 法则)

> 面试用,2-3 分钟讲清一个项目。每个故事标注了【核心考点】和【追问应对】。
> 基于用户背景:华为 HarmonyOS 移动开发 → 转 Agent 方向。

---

## 故事一:企业知识库 RAG Agent(推荐主讲故事)

### Situation(背景)

在华为终端业务部门,团队内部有大量技术文档(FAQ、wiki、需求文档、代码规范等),散落在多个平台。新员工入职后,平均需要 2-3 周才能独立上手开发,大量时间花在"找文档、问同事"上。团队希望构建一个智能问答 Agent,让新人能直接用自然语言提问,快速获取准确答案。

### Task(任务)

我负责设计和实现这个知识库问答 Agent 的核心链路,具体目标:
1. **准确率**:回答 Faithfulness ≥ 0.85,Answer Relevancy ≥ 0.80
2. **延迟**:P95 延迟 < 3 秒
3. **覆盖**:支持中文文档为主,含部分英文技术文档
4. **可维护**:运营人员可自行上传/更新文档,无需开发介入

### Action(行动)

**1. 数据处理与分块策略**
- 解析 PDF/Word/wiki HTML,统一转为 Markdown
- 采用**递归分块**:先按段落(分隔符 `\n\n`),再按句子,目标 chunk size 512 token,overlap 64 token
- 对表格和代码块做特殊处理:整块保留不分切,避免语义断裂
- 为每个 chunk 添加 metadata(来源、标题层级、时间戳),辅助后续过滤

**2. 检索链路设计**
- **混合检索**:BM25(关键词) + 向量检索(bge-large-zh,1024 维) → RRF 融合(k=60)
- **Query 改写**:用 LLM 做 HyDE(先生成假设性答案,再用答案检索)和 Multi-Query(生成 3 个改写版本并行检索)
- **Rerank**:用 bge-reranker-large 对 Top-20 重排,取 Top-5 喂给 LLM
- 向量库选用 **Milvus**(文档量约 10 万级,HNSW 索引,M=16,efConstruction=256,efSearch=64)

**3. Agent 编排**
- 使用 **LangGraph** 构建状态图,支持检索门控:LLM 先判断是否需要检索,避免简单问题浪费检索资源
- 对多跳问题(如"A 技术和 B 技术的区别?"),实现**迭代检索**:第一轮检索后,LLM 判断信息是否充分,不充分则生成 follow-up query 再检索
- 上下文组装:按相关度排序,加上文档来源标注(`[来源: xxx.pdf, 第3页]`),实现答案溯源

**4. 评估与优化**
- 用 **RAGAS** 框架离线评估:构建 200 题测试集(含简单/多跳/拒绝回答三类)
- 初始 Faithfulness 只有 0.72,排查发现是**分块太大**导致噪声 → 调小 chunk size 到 384,Faithfulness 提升到 0.86
- Answer Relevancy 0.74 → 加 Query 改写后提升到 0.83
- 延迟优化:将 Rerank 从 cross-encoder 在线推理改为**批量调用 + 缓存高频 Query 的检索结果**,P95 从 5.2s 降到 2.8s

### Result(结果)

- **准确率**:Faithfulness 0.86,Answer Relevancy 0.83,Context Recall 0.89
- **延迟**:P95 2.8s,P50 1.5s
- **业务效果**:新员工日均提问量 200+,文档查找时间从平均 15 分钟降到 2 分钟,入职上手周期缩短至 1 周
- **可维护性**:运营上传文档后自动触发增量索引,5 分钟内可检索

### 【核心考点】
- RAG 全链路理解(分块→Embedding→检索→Rerank→生成)
- 混合检索 + RRF 融合原理
- Query 改写(HyDE / Multi-Query)
- RAGAS 评估框架
- LangGraph 状态图编排
- 迭代检索 / 检索门控

### 【追问应对】

| 追问 | 回答要点 |
|------|---------|
| 为什么选 bge 而不是 OpenAI embedding? | 中文场景 bge 效果好、可本地部署、无数据外泄风险(华为合规要求) |
| RRF 为什么 k=60? | 原论文推荐值,对排名差异不敏感;实测 k=40-80 效果差异不大 |
| 如何处理文档更新? | 增量索引:按文档 ID + 版本号管理,更新时删除旧 chunk 再插入新 chunk |
| 知识库没有的问题怎么处理? | 检索门控:Top-K 相关度低于阈值时,LLM 直接回答"知识库中未找到相关内容",避免幻觉 |
| 如何降低 LLM 成本? | 缓存高频 Query;简单问题用小模型(Qwen-7B)路由;Prompt 压缩(LLMLingua) |
| 如果文档量到千万级? | Milvus 分区+分片;HNSW 换 IVF-PQ 降低内存;冷热分离 |

## 故事二:Multi-Agent 代码审查系统

### Situation(背景)

团队代码审查依赖人工,每个 MR 平均等待 4-6 小时才有人 review,且审查质量参差不齐(风格问题多花时间,深层逻辑问题容易漏)。团队希望用 Agent 辅助代码审查,在 MR 提交后自动生成审查意见,人工只需确认。

### Task(任务)

设计并实现一个 Multi-Agent 代码审查系统:
1. 自动分析 MR diff,生成结构化审查意见
2. 覆盖三层:代码风格 → 逻辑缺陷 → 安全风险
3. 误报率 < 15%(过高会浪费开发者时间)
4. 与现有 CodeHub(内部 Git 平台)集成,自动评论

### Action(行动)

**1. Multi-Agent 架构设计**

采用**层级(Hierarchical)模式**:

```
Orchestrator(编排 Agent)
├── Style Agent(风格检查:命名、注释、格式)
├── Logic Agent(逻辑检查:边界条件、空指针、并发问题)
└── Security Agent(安全检查:注入、硬编码密钥、权限)
```

- Orchestrator 负责分发任务、汇总结果、去重合并
- 三个子 Agent 并行执行,各自专注一个维度
- 用 **LangGraph** 实现,每个 Agent 是一个节点,Orchestrator 是入口和出口

**2. 上下文构建**
- 不只看 diff,还拉取**调用链**(被修改函数的调用方)和**类定义上下文**
- 用 tree-sitter 做代码 AST 解析,提取函数签名、依赖关系
- 上下文窗口管理:diff + 上下文控制在 8K token 内,超出则截断远端代码

**3. 降低误报**
- **双重确认机制**:Agent 发现问题后,用第二个 LLM 调用做"验证 pass"(判断是否真正问题)
- **历史学习**:收集开发者 "Ignore" 的评论,作为 few-shot 反例,减少同类误报
- **严重度分级**:Critical / Warning / Suggestion,只有 Critical 自动评论,其他标记为建议

**4. 工具集成**
- Agent 可调用工具:读取完整文件、搜索代码库、查看提交历史、查询测试覆盖率
- MCP 协议封装内部 API(代码库搜索、MR 评论),便于复用

### Result(结果)

- **检出率**:逻辑缺陷检出率 68%(人工 review 基线约 55%)
- **误报率**:12.3%(低于 15% 目标)
- **效率**:MR 首次审查从 4 小时缩短到 5 分钟(Agent 自动审查)
- **采纳率**:开发者采纳或讨论 Agent 意见的比例 41%
- **覆盖**:安全维度新增检出 SQL 注入 2 处、硬编码 token 5 处(之前人工漏检)

### 【核心考点】
- Multi-Agent 协作模式(层级模式)
- LangGraph 并行节点编排
- 代码 AST 解析 + 上下文构建
- 降低 LLM 误报的策略(双重确认、历史学习、严重度分级)
- MCP 协议工具集成
- Agent 评测(检出率/误报率/采纳率)

### 【追问应对】

| 追问 | 回答要点 |
|------|---------|
| 为什么不用单 Agent? | 单 Agent 上下文太长、注意力分散;多 Agent 分工后每个上下文精简,专业度更高 |
| 三个 Agent 结果冲突怎么办? | Orchestrator 做合并去重;同一行有多个意见时按严重度排序,Critical 优先 |
| 为什么不直接用 SonarQube? | SonarQube 擅长规则匹配,但对复杂逻辑缺陷(如并发问题、业务逻辑)无能为力;Agent 能理解语义 |
| 如何处理超长 MR? | 按 文件/函数 粒度分批处理;每批独立生成意见后合并;超 1000 行的 MR 标记为"需人工重点审查" |
| 成本怎么样? | 每个 MR 平均消耗 15K token,约 ¥0.3/次;月均 2000 MR,总成本约 ¥600/月,可接受 |
| Agent 自身会不会有安全风险? | 代码不外传(用内部部署的模型);Agent 只有只读权限,不能修改代码;评论内容经过敏感信息过滤 |

## 故事三:Agent 性能优化——从 5 秒到 1 秒(推荐加分故事)

### Situation(背景)

知识库 Agent 上线后用户反馈"回答慢",P95 延迟 5.2 秒。产品方要求优化到 P95 < 2 秒,但不能降低回答质量。

### Task(任务)

在不降低回答准确率的前提下,将 Agent 端到端延迟从 P95 5.2s 优化到 2s 以内。

### Action(行动)

**1. 全链路延迟分析**

先用 **Langfuse** 做 Tracing,拆解各阶段耗时:

| 阶段 | 耗时(P95) | 占比 |
|------|-----------|------|
| Query 改写(LLM) | 0.8s | 15% |
| 向量检索(Milvus) | 0.3s | 6% |
| BM25 检索 | 0.1s | 2% |
| Rerank | 1.2s | 23% |
| 上下文组装 | 0.1s | 2% |
| LLM 生成 | 2.5s | 48% |
| 其他(网络/序列化) | 0.2s | 4% |

瓶颈:**LLM 生成(48%)** 和 **Rerank(23%)**。

**2. 针对性优化**

**优化 1:LLM 生成——流式输出 + Speculative Decoding**
- 开启 LLM 流式输出(stream=True),用户看到第一个 token 的时间从 2.5s 降到 0.5s(首 token 延迟 TTFT)
- 虽然总生成时间不变,但**用户体感延迟大幅降低**(用户在等待中看到输出)
- 用小模型(Qwen-7B)做投机解码草稿,大模型(Qwen-72B)验证,总生成时间减少 35%

**优化 2:Rerank——缓存 + 批量 + 降级**
- **缓存**:对高频 Query 的 Rerank 结果缓存(TTL 1 小时),命中率 28%
- **批量**:原方案逐条 Rerank,改为批量调用(bge-reranker 支持 batch),吞吐提升 3x
- **降级**:简单 Query(检索 Top-1 相关度 > 0.9)跳过 Rerank,直接用向量检索结果

**优化 3:Query 改写——异步并行**
- HyDE 和 Multi-Query 原本是串行的,改为**并行执行**(asyncio.gather),Query 改写阶段从 0.8s 降到 0.4s
- 对高频 Query 缓存改写结果

**优化 4:Embedding——本地化**
- 原方案调远程 Embedding API(网络延迟 200ms),改为本地部署 bge 模型,延迟降到 30ms

**优化 5:检索——预热 + 连接池**
- Milvus 连接池预热,避免冷启动
- HNSW 参数调优:efSearch 从 64 降到 48(精度几乎无损,检索延迟降 30%)

### Result(结果)

| 指标 | 优化前 | 优化后 | 变化 |
|------|--------|--------|------|
| P95 总延迟 | 5.2s | 1.9s | -63% |
| P50 总延迟 | 3.1s | 1.2s | -61% |
| 首 token 延迟 | 2.5s | 0.5s | -80% |
| 准确率(Faithfulness) | 0.86 | 0.85 | -0.01(可接受) |

**关键经验**:延迟优化要先做 Tracing 拆解,找到真正的瓶颈再针对性优化,避免"盲目优化"。

### 【核心考点】
- Agent 可观测性(Langfuse Tracing)
- 全链路延迟拆解方法论
- 流式输出 / Speculative Decoding
- 缓存策略(Query 缓存、Rerank 缓存)
- 异步并行(asyncio.gather)
- 性能 vs 质量的权衡

### 【追问应对】

| 追问 | 回答要点 |
|------|---------|
| 投机解码原理? | 小模型先快速生成候选 token,大模型并行验证;匹配的 token 直接接受,不匹配的从断点重新生成 |
| 缓存一致性? | 文档更新时清除相关 Query 的缓存(按文档 ID 反查);设 TTL 兜底 |
| efSearch 降了精度真没影响? | 测试集上 Recall@5 从 0.91 降到 0.89,但下游 Faithfulness 几乎不变(因为 Rerank 会重排) |
| 如果要进一步优化? | 模型量化(INT8/INT4)、KV-Cache、Continuous Batching、边缘部署 Embedding |
| 如何保证优化不引入 bug? | 每次优化后跑 200 题测试集回归,延迟和准确率双重卡点;AB 测试灰度 10% 流量验证 |

## 面试使用指南

### 讲述节奏(每个故事 2-3 分钟)

```
30s  → Situation(背景:谁、做什么、遇到什么问题)
30s  → Task(目标:量化指标)
60s  → Action(核心 2-3 个技术决策,不要流水账)
30s  → Result(量化结果 + 业务价值)
```

### 故事选择策略

| 面试场景 | 推荐故事 |
|---------|---------|
| RAG/检索相关岗位 | 故事一(知识库 RAG) |
| Agent 框架/Multi-Agent | 故事二(代码审查 Multi-Agent) |
| 工程性能/线上优化 | 故事三(性能优化) |
| 通用/开放性问题 | 故事一(最全面,覆盖 RAG+评估+LangGraph) |

### 注意事项

1. **诚实**:面试官会追问细节,编造的故事经不住 3 层追问。如果项目是学习项目而非真实生产项目,可以说"我在学习期间做了一个实战项目..."
2. **量化**:用数字说话(P95 5.2s→1.9s 比"优化了性能"强 10 倍)
3. **深度 > 广度**:宁可讲透 1 个技术决策,也不要蜻蜓点水 5 个
4. **反思**:主动说"如果重来,我会..."展示成长思维
5. **结合岗位**:根据面试的岗位 JD,调整故事的重点(偏 RAG 就多讲检索,偏工程就多讲优化)

> **最后提醒**:这三个故事覆盖了 Agent 面试的三大核心维度——RAG 知识(故事一)、Multi-Agent 架构(故事二)、工程优化(故事三)。面试前对每个故事练习 2-3 遍,确保 2 分钟内能流畅讲完,并准备好 3 层追问的应对。
