## 一、Agent 基础

**Q1　Agent 和 Chatbot、Workflow 的区别？**
A：Chatbot 单轮对话；Workflow 路径固定、由人预先编排；Agent 由模型自主决策下一步走哪、调哪个工具。

**Q2　agent 的完整公式？**
A：`Agent = Harness + Model + Loop + Tools + Memory`。模型是大脑，Harness 是身体——模型负责想，Harness 负责做。

**Q3　什么是 Harness？为什么说它是生产级壁垒？**
A：包裹模型的运行时框架，负责执行循环、上下文管理、工具注册调度、权限控制、错误处理、可观测性。模型差距在缩小，同一模型换 Harness 任务成功率可从 40% → 80%；Claude Code / Cursor / OpenHands 的核心都是 Harness 工程。

**Q4　ReAct 的原理？和 CoT 的区别？**
A：Reasoning + Acting 交织，每轮 Thought → Action → Observation 循环，直到输出 Final Answer。CoT 只推理不行动；ReAct 引入工具调用与环境反馈闭环。

**Q5　ReAct 的缺陷怎么补？**
A：错误累积 → 加 Reflection / Self-Refine；上下文膨胀 → 摘要压缩 + 滑动窗口；无全局规划 → Plan-and-Execute / ReWOO。

**Q6　Function Calling 的本质？**
A：模型输出结构化 JSON（工具名 + 参数），**模型不执行函数**，由 Harness 执行后把结果作为 observation 喂回，再进入下一轮。

**Q7　工具数量多了会怎样？**
A：超过 10–15 个时模型选择准确率明显下降。解法：工具分组路由、按意图动态挂载、拆成 Multi-Agent 分工。

**Q8　MCP 是什么？和 Function Calling 什么关系？**
A：Model Context Protocol，Anthropic 提出的工具协议标准（"AI 的 USB-C"）。MCP 是**协议层**（标准化接口，Host ← stdio/SSE → Server → Tools/Resources/Prompts），Function Calling 是**模型能力**。价值是工具一次开发、多模型通用。

**Q9　Agent 记忆怎么设计？**
A：短期用上下文窗口；长期分语义（事件）/ 程序（技能）/ 情景（画像），落向量库或知识图谱；外部记忆用向量库。评分公式 `0.45×sim + 0.20×recency + 0.20×importance + 0.15×frequency`，recency 用 `e^(-λΔt)`，λ≈0.995。

**Q10　怎么防止 Agent 死循环？**
A：三层防护——① 步数硬上限（如 8 步）；② 连续相同 `(tool, args)` 检测到即 break；③ 工具连续失败 N 次即禁用。再加 prompt 软约束，可拦掉约 80% 潜在死循环。

## 二、RAG 与检索

**Q11　RAG 全链路？**
A：离线=解析 → 清洗 → 分块 → Embedding → 向量库；在线=Query 改写 → Embedding → 检索 → Rerank → 上下文组装 → LLM 生成。

**Q12　分块策略怎么选？**
A：固定长度（512 token + 50–100 overlap）通用；递归分块（先段落再句子）最常用；按标题层级保留结构；父子分块用小 chunk 检索、大 chunk 供上下文，能显著降幻觉。

**Q13　为什么固定长度切分不好？**
A：会把表格和代码块切烂、切断语义。做法是结构化内容整块保留，或改按结构/语义切分。

**Q14　RRF 是什么？k 为什么取 60？**
A：`RRF(d) = Σ 1/(k + rank_i(d))`，把多路检索的排名融合，不需要分数量纲对齐。k=60 是原论文推荐值，实测 40–80 差异不大——**真正敏感的是召回路数**，3 路（向量+BM25+HyDE）反因冗余而降分，2 路常最优。

**Q15　混合检索为什么有效？**
A：向量擅长语义相似，BM25 擅长专有名词、编号、型号精确匹配。二者互补，融合后召回更稳。

**Q16　HyDE 是什么？代价？**
A：先让 LLM 生成"假设性答案"，再用它去检索。可把 Recall@10 从 76% → 83%，代价是多一次 LLM 调用（约 +400ms），用 mini 模型约 $0.0005/次。缓解编造：prompt 约束"不要编造具体数字和日期"，仅对短 query 使用。

**Q17　怎么降低幻觉？**
A：检索约束（只用上下文回答）+ 父子文档扩展上下文 + 引用溯源（标注来源）+ 检索门控（相关度低于阈值直接答"知识库中未找到"）+ 输出校验 + 人工兜底。

**Q18　Agentic RAG 和传统 RAG 的区别？**
A：传统 RAG 单次检索、流程固定；Agentic RAG 支持检索路由、迭代/多跳检索、检索门控（LLM 判断是否需要检索）。

**Q19　GraphRAG 适用什么场景？**
A：全局性问题（"整个文档集的主要主题是什么"）。流程是 LLM 抽实体关系 → 建图谱 → Leiden 社区检测 → 生成社区摘要 → 全局查询汇总摘要。Leiden 优于 Louvain（保证社区连通性）。

**Q20　向量库怎么选？**
A：Milvus（亿级、分布式）｜Qdrant（Rust、过滤强）｜Chroma（轻量原型）｜pgvector（已有 PG、小规模）｜Elasticsearch（已有 ES、混合检索）。参数：HNSW 的 M 16–48 / efConstruction 200–400 / efSearch 50–200；IVF 的 nlist ≈ √N~4√N。

**Q21　上下文太长怎么办？**
A：注意 Lost in the Middle（中间信息易被忽略）。手段：LLMLingua 压缩 2–20x、Token 预算分配（System 10% / 检索 40% / 历史 30% / 输出 20%）、相关优先 + 最新优先 + 摘要替代旧历史。

**Q22　RAG 怎么评估？**
A：RAGAS 四指标——Faithfulness（答案可被上下文支撑的比例）、Answer Relevancy（反推问题相似度）、Context Precision（相关文档排名加权）、Context Recall（ground truth 覆盖率）。检索侧看 Recall@K / MRR / NDCG。**每个数字要说清测试集来源、标注方式、指标定义。**

## 三、框架与编排

**Q23　LangChain 和 LangGraph 的区别？**
A：LangChain 是 Chain 链式、无状态、不支持循环；LangGraph 是 StateGraph 图状、显式状态管理、支持 cycles，适合 Agent / 多步 / 多 Agent，并有 Checkpointing 持久化。

**Q24　LangGraph 的 Reducer 是干什么的？**
A：控制状态字段的合并方式。默认是覆盖，`Annotated[list, add]` 或 `add_messages` 则是追加。多节点并发写同一字段时必须用 Reducer，否则互相覆盖。

**Q25　动态路由怎么实现？**
A：`add_conditional_edges` 按状态返回下一节点名；或 `Command(goto="node", update={...})` 在节点内同时改状态和跳转。

**Q26　人机协同（HITL）怎么做？**
A：`interrupt_before=["tools"]` 在工具执行前暂停；或节点内 `interrupt({...})` 主动请求输入。恢复用 `invoke(None, config)` 或 `Command(resume=value)`。典型场景：转账超阈值、退款、投诉类敏感操作需人工审批。

**Q27　持久化和多用户隔离？**
A：Checkpointer 每超级步存快照——MemorySaver（内存）/ SqliteSaver / PostgresSaver。用 `thread_id` 隔离会话，`get_state_history` 可做时间旅行回滚。

**Q28　什么时候不该用框架？**
A：需要精细控制上下文组装、循环终止、工具重试策略时，自研更可控。实测同一需求手写约 500 行、LangChain 版约 200 行，但框架在 Agent Executor 上单步开销更多、依赖更重。

**Q29　Multi-Agent 有哪几种编排模式？**
A：Hierarchical（层级）、Sequential（串行）、Parallel（并行）、Debate（辩论）、Network（网络）。工程上最常用 Supervisor（中心化）与 Swarm（去中心化 handoff）。

**Q30　什么时候该拆 Multi-Agent？**
A：单 Agent 上下文太长、注意力分散、工具过多（>10–15）选择不准时。拆分后每个 Agent 上下文精简、专业度更高。代价是通信成本与状态一致性复杂度。

**Q31　多 Agent 结果冲突怎么办？**
A：编排者做合并去重；同一位置多条意见按严重度排序（Critical 优先）；或用仲裁 Agent / 辩论多轮 + 裁判。

**Q32　Agent 间怎么通信？**
A：共享 State（LangGraph 主流）、消息传递（Message Passing）、黑板模式（Blackboard）。共享 State 最简但对状态结构设计要求高。

**Q33　怎么保证 Multi-Agent 一定收敛？**
A：设 `recursion_limit`；定义明确终止条件；加质量门控但设迭代上限（如迭代 ≥4 次强制收尾）；给每个子任务加超时。

## 四、系统设计与评测

**Q34　Agent 系统设计怎么答？**
A：六步——需求澄清（QPS/延迟/精度/成本/多轮）→ 架构设计（单体 or 多 Agent、同步 or 异步）→ 核心模块（API → 编排 → 检索 → 工具 → 记忆 → 监控）→ 技术选型 → 容量规划（QPS × Token × 价格）→ 兜底策略（降级/限流/熔断/人工）。

**Q35　延迟怎么优化？**
A：先 Tracing 拆解定位真瓶颈，再对症下药——流式输出降首 token 延迟、缓存高频 Query、批量调用、异步并行（`asyncio.gather`）、Embedding 本地化、降级跳过非必要步骤（如高相关度时跳过 Rerank）。

**Q36　成本怎么降？**
A：多级缓存（LLM / Rerank / Embedding / 语义缓存）+ 模型分级路由（轻量模型判复杂度）+ Prompt 压缩 + 减少 top_k + 批处理。

**Q37　怎么做 Agent 评测？**
A：三层——组件级（单元测试）、端到端级（Golden Set）、在线级（A/B + 监控）。方法有关键词匹配、LLM-as-Judge、轨迹评测（工具覆盖率 / 违规调用 / 步骤效率 / 冗余调用）、精确匹配。**评测要从第一天建，不能等上线补。**

**Q38　LLM-as-Judge 怎么保证可信？**
A：四道防线——双裁判取平均（分歧大触发人工复核）、拆多维度加权打分、用人工双盲 golden set 校准（Pearson < 0.7 视为跑偏）、顺序随机化消除位置偏见。

**Q39　评测集怎么构建？**
A：分层抽样：按类目（如请假/报销/差旅/制度/福利）× query 长度（短/中/长）分层，配比常见 / 边界 / 对抗三类，定期更新。

**Q40　线上出故障怎么排查？**
A：先建可观测（Trace/Span/Event 三层 + 分阶段耗时打点），再按"是模型问题还是 Harness 问题"二分。典型事故：向量库 compaction 误配到业务高峰导致召回骤降——靠稳定性 SLO（检索 P99 < 200ms、召回波动 < 5%）提前发现。

**Q41　怎么做降级？**
A：分层——① 向量库多副本；② 全文检索（BM25）fallback，召回会降但可用；③ 缓存兜底；④ 直连 LLM + 免责声明。配熔断（延迟超阈值自动降级）与告警。

**Q42　Agent 有哪些安全风险？**
A：OWASP LLM Top 10 核心——Prompt Injection、不安全输出处理、训练数据投毒、模型 DoS、供应链。防御：分离系统指令与用户输入、输入过滤、工具最小权限 + 白名单 + 高危操作人工审批、输出 Schema 校验、代码沙箱执行。

**Q43　A/B 实验怎么设计？**
A：实验组 10% / 对照 90%，按 user_id 哈希分流；定核心指标 + 护栏指标（如 P99 不升超 20%）；算样本量 `n = 16σ²/Δ²`；显著性要求 ≥7 天且样本量足够；中途偷看只记录不决策（用序贯检验）。

**Q44　SLO 和 Error Budget？**
A：定义可用性与性能目标（如端到端可用性 > 99.5%、检索 P99 < 200ms），Error Budget 是允许的失败额度（如每月 0.5%）。用掉一半暂停开发、用完停发新功能。

## 五、LLM 底层

**Q45　Self-Attention 公式？为什么除以 √dk？**
A：`Attention(Q,K,V) = softmax(QK^T/√dk) × V`。dk 大时点积方差大，softmax 进饱和区梯度趋近 0；除以 √dk 使方差稳定为 1，梯度健康。

**Q46　Multi-Head 的作用和参数量？**
A：并行 h 个头在不同子空间学不同关系，再 concat 后线性变换 Wo。参数量 4 × d_model²（Q/K/V/O 各一个）。

**Q47　位置编码有哪些方案？**
A：Sinusoidal（可外推、无需学习）、Learned（灵活但不可外推）、RoPE（旋转矩阵编码相对位置，主流，LLaMA）、ALiBi（attention bias 按距离衰减，极简）。

**Q48　预训练 → SFT → RLHF 各自做什么？**
A：预训练在海量无标注语料学语言与知识；SFT 用指令数据教会遵循指令；RLHF 用人类偏好训 Reward Model + PPO 对齐人类偏好。DPO 是直接偏好优化，省掉 RM。

**Q49　LoRA 原理？**
A：冻结原权重，注入低秩矩阵 `W = W₀ + BA`（B∈R^(d×r)、A∈R^(r×d)、r ≪ d），只训 0.1–1% 参数。QLoRA 再加 4bit 量化基座。

**Q50　推理优化有哪些手段？**
A：KV-Cache（2–4x）、Flash Attention（2–3x）、PagedAttention（显存利用率↑）、量化 INT8/INT4（显存减半、2x）、投机解码（1.5–2x）、Continuous Batching（吞吐 5–10x）。

**Q51　投机解码原理？**
A：小模型先快速生成候选 token，大模型并行验证；匹配的直接接受，不匹配的从断点重新生成。

**Q52　Tokenizer 和 Token 成本的关系？**
A：中文约 1.4–1.5 字/token，英文约 4 字符/token，代码效率更低。这直接决定上下文能装多少、以及按 token 计费的成本。

## 六、项目与简历追问（结合本人经历）

**Q53　一句话介绍你最拿手的项目？**
A：CodeAgentHarness——跑在华为内源平台的编程智能体，做自动改代码和自动代码审查，我独立从 0 到 1 完成，被内部多个团队试用。

**Q54　为什么自己写 Harness 而不用现成框架？**
A：要的是**可控性**。框架封装了循环，但上下文怎么裁、工具怎么失败重试、权限怎么卡，恰恰是我最需要控制的点。先手写过一遍，所以后来上手 LangGraph 时知道它每个机制在解决什么、什么时候不够用。

**Q55　这个项目最难的地方？**
A：四点——① 上下文裁剪（按文件/符号粒度召回 + 动态裁预算）；② 保证停下来（步数上限 + 重复动作检测 + 连续失败禁用工具）；③ 不闯祸（工具白名单 + 读写权限分离 + 命令超时沙箱 + 改动必须人工确认）；④ 故障归因（分阶段耗时与 Token 打点，区分模型问题还是 Harness 问题）。

**Q56　你的 Agent 经验都是自学的，怎么证明不是纸上谈兵？**
A：三个标准——能跑（项目本地可运行，不是伪代码）、能说数字（手写版 500 行 vs 框架版 200 行；RRF k 取 60 的依据）、知道边界（会主动承认哪些是猜的、哪些没做过）。

**Q57　华为笔记的经历和 Agent 有什么关系？**
A：同一组难题换了对象——复杂状态管理 → 消息/工具/记忆状态；增量渲染 → 流式 token 输出；长文档性能优化 → 上下文预算与 Token 成本控制。所以是能力迁移，不是从零转行。

**Q58　你从客户端转过来，比算法背景的人强在哪？**
A：工程落地能力（服务化、缓存、限流、降级、监控、回归）、对延迟与流式渲染的肌肉记忆、以及从 Harness 细节出发理解 Agent 的视角——而行业共识恰好也是壁垒在 Harness。

**Q59　业余做游戏对做 Agent 有帮助吗？**
A：有。Godot 里用状态机驱动角色行为和关卡流程——每个状态有进入条件、退出条件、超时兜底。ReAct 循环、LangGraph 状态图、多 Agent 阶段流转本质是同一类问题：怎么定义状态、怎么控制迁移、怎么保证收敛。

**Q60　给你一个 Agent 项目，3 个月怎么落地？**
A：前 2 周不写 Agent，先采样真实问题分类、确认知识源与评估标准；第 1 个月做 MVP（只接核心工具 + 同步建 Golden Set 与 Trace，目标准确率 > 70%、拒答率 < 20%）；第 2 个月按 bad case 归因驱动迭代（高频易修优先），补上下文工程、缓存与降级；第 3 个月扩工具与规模化（工具调用准确率达标再加），补监控、SLO 与灰度。原则：**先证明价值，再扩能力；评测与可观测跟功能同步建。**

## 七、软性问题与反问

**Q61　为什么离职？**
A：① 方向——想做 Agent 工程，而岗位是移动端业务交付；② 成长曲线——外包编制难参与架构选型。在方向明确后主动离开，全职转向。

**Q62　为什么选我们公司 / 这个岗位？**
A：说清三点——公司在 Agent 上的真实投入（产品 / 技术栈）、岗位职责与我的能力交集、我能贡献的具体点（Harness 工程、RAG 链路、评测体系）。**不要泛泛夸公司。**

**Q63　你的职业规划？**
A：0–3 个月吃透现有系统、从高频 bad case 做出可见改进；1–2 年独立负责一条 Agent 链路；3–5 年做纵深、带团队定标准。

**Q64　你最大的缺点？**
A：说真实且已在改进的——如"算法理论是短板（非科班），所以把力气放在工程侧，并强制自己把模型原理讲到 Transformer / SFT / RLHF 这一层"。

**Q65　怎么快速上手一个陌生的 Agent 代码库？**
A：先跑通主链路并打开 Trace 看一次完整调用；再顺着「入口 → 编排 → 检索 → 工具 → 状态」读；最后用 Golden Set 跑一遍基线，拿到可对比的数字再动手。

**Q66　平时怎么跟进 Agent 领域？**

**Q70　你怎么衡量一个 Agent 做得好不好？**
A：业务侧看一次解决率 / 转人工率 / 满意度；技术侧看检索 Recall@K、Faithfulness、幻觉率、拒答准确率、引用准确率；工程侧看 P95 延迟、单次 Token 成本、工具调用准确率。三层都要有，否则优化会跑偏。

**Q71　文档更新了怎么办？**
A：增量索引——按文档 ID + 版本号（或 md5 指纹）判断变更，只删除旧 chunk 再插入新 chunk，避免全量重建；旧版本保留一段时间可回滚；定期全量对账。

**Q72　怎么决定该不该上 Agent（而不是纯 RAG）？**
A：看问题分布。如果 90% 是 FAQ 与单点检索，纯 RAG 更稳更便宜；只有多步推理、需要调外部系统、需要多轮决策时才引入 Agent。引入前先量化风险——工具调用准确率业界约 70–80%，叠加后可能让端到端准确率下降，所以先接 1 个工具灰度验证。
